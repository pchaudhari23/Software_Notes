## 1. Fundamentals

- **Database:** Organized collection of data, which can be **stored** electronically, **retrieved** and **modified**.
- **DBMS (Database Management System):** Software that **creates, manages, and controls access** to databases (e.g., **MySQL, PostgreSQL, Oracle**).
- The data may be stored **physically** in any **mass storage device** such as flash memory or hard drive, but **logically or virtually**, it is stored in a **database**.
- A person **who works with databases** is called a **Database Admin** or **Database Administrator** or **DBA**.
- Examples: MySQL (pronounced my-sequel), PostgreSQL (Postgres), MongoDB, Oracle Database etc.
  - *Correction:* 'Procedural SQL' is not a database. **PL/SQL** is Oracle's procedural extension of SQL (PostgreSQL has PL/pgSQL).
- Structured (relational, SQL) database: Database => Tables => Records (rows)
- Document (NoSQL) database, MongoDB: Database => Collections => Documents
  - *Correction:* MongoDB is not 'unstructured'. It is **semi-structured / schema-flexible**. 'Unstructured' describes raw text, images, logs.

See document 2 (Structured DB) and document 3 (MongoDB) for the details of each.

## 2. The 10 first principles

Every database feature solves one of these problems. For any feature ask: **which principle does it solve, and what does it cost?**

| # | Principle | Derives | Cost |
| --- | --- | --- | --- |
| 1 | Memory is volatile, disk is durable | Write-ahead log, durability (D in ACID), crash recovery | Slower writes |
| 2 | Disk is slow, random access is far worse than sequential | B-trees (few disk hops), buffer pool / caching, append-only logs | Memory use |
| 3 | Searching without structure is O(N) | Indexes | Extra storage, every write updates the index |
| 4 | Data duplicated in two places will eventually disagree | Normalization | Joins needed to put it back together. Denormalization / embedding is the reverse trade |
| 5 | Concurrent users touching the same data interleave unpredictably | Transactions, isolation levels, locks, MVCC | Stronger isolation = less concurrency |
| 6 | Operations can fail halfway | Atomicity, rollback, idempotency | Overhead of logging |
| 7 | Machines die | Replication | Replicas lag, so reads can be stale |
| 8 | One machine has a ceiling | Partitioning, sharding | Cross-shard queries and transactions get hard, bad shard key = hotspots |
| 9 | A network partition forces a choice between consistency and availability | CAP, eventual consistency, BASE | Give up one of C or A during a partition |
| 10 | Structure enforced early catches bugs early, flexibility ships faster | Fixed schema (SQL) vs flexible documents (Mongo) | Rigidity vs risk of messy data |

Principles 1 and 2 are the foundation. 3 to 10 each solve a problem those two create or leave open.

## 3. Performance (principles 2, 3, 8 in action)

**Analogy.** Say I give you 10 books of 1000 pages each and ask a question whose answer lies in one of the books.

- **Case 1:** You start reading from book 1 and find the answer somewhere on page 720 in book 7. The time taken to read the first six books was wasted. This time is also variable: one question's answer could be in the first book, another in the last.
- **Case 2:** You don't read all books yourself but distribute them to ten friends. Only the friend reading the book with the answer did worthy effort, the others' efforts are wasted.
- **Case 3:** You give an appendix at the end of every book. Less time to search for a word on a page, but all ten people still have to search their appendix.
- **Case 4:** Tear the appendix out of all books and store it in one book, held by a person called master. Now when a question is asked he looks it up in the appendix, finds which book has the answer, and only that person has to search it.

**Analysis**

**Case 1 - Full Table Scan (linear search)**

- No index exists, so the database reads every row sequentially.
- Query time is proportional to table size (O(N)).
- Most data read does not contribute to the final answer.

**Case 2 - Parallel Full Table Scan**

- Table is scanned simultaneously by multiple CPU cores or nodes.
- Response time improves, but total work remains the same.
- Most parallel workers still perform unnecessary reads.

**Case 3 - Local Index per Partition**

- Each shard has its own index to speed up local searches.
- Query is still sent to all shards due to lack of global routing.
- Only one shard returns results, the others do wasted index lookups.

**Case 4 - Global Index with Query Planner**

- Central index and metadata identify the correct shard and index.
- Only relevant data is accessed using index seeks (O(log N)).
- Minimal I/O and CPU usage with predictable query performance.

*(added)* Case 4 combines two ideas: an **index** (finding rows fast) and **routing** (finding the right shard). Keep them separate when explaining.

## 4. Indexing (principle 3)

Indexing is a technique used to **speed up data retrieval** from a database.

**How it works**

- Creates a data structure (usually B-tree or Hash)
- Allows faster search instead of full table scan
- **Cost** (added): takes extra storage, and every insert/update/delete must also update the index, so reads get faster and writes get slower.

**Types of indexes**

- **Primary Index:** Index created automatically on primary key.
- **Secondary Index:** Index created on non-primary columns.
- **Composite Index:** Index created on multiple columns (**order matters**). (added) It is sorted by the first column, then the second within it, so a query that skips the first column can't use it.
- **Clustered Index:** Determines the physical order of data storage. (added) In MySQL InnoDB the table is clustered by primary key.
- **Non-clustered Index:** Separate structure pointing to table rows.

## 5. Transactions (principles 5 and 6)

A transaction is a **sequence of database operations** performed as a **single logical unit of work**.

**ACID:** Atomicity, Consistency, Isolation, Durability.

- **Atomicity:** Ensures all operations in a transaction succeed or fail together.
- **Consistency:** Ensures the database moves from one valid state to another.
- **Isolation:** Ensures concurrent transactions do not interfere with each other.
- **Durability:** Ensures committed data is permanently stored.

(added) **Isolation levels** (weakest to strongest): Read Uncommitted, Read Committed, Repeatable Read, Serializable. The problems they prevent: **dirty read** (reading uncommitted data), **non-repeatable read** (same row gives different values in one transaction), **phantom read** (a repeated query returns new rows). Defaults: PostgreSQL = Read Committed, MySQL InnoDB = Repeatable Read.

## 6. Scaling and storage (principles 7 and 8)

**REPLICATION:** The process of **copying data from one database server to another**. Often done by adding a read replica. The primary (older term: master) handles the writes, and replicas need to be kept in sync.

**PARTITIONING:** Dividing a **single large table** into smaller pieces. Still resides on the same database server. Improves query performance and manageability.

**SHARDING:** Distributing data **across multiple database servers**. Each shard holds a subset of data. Used in large-scale, high-traffic systems. Distribution is done based on the **shard key**. A poor shard key can lead to performance issues.

**RAID:** A **data storage technology** that combines **multiple physical disks** into a **single logical unit** to improve **performance**, **fault tolerance**, or **both**. (It works at the storage level, below the database.)

## 7. Database design and data modeling (principles 4 and 10 applied)

- **Database design:** Process of defining the structure of the DB, entities and relationships with each other. ER diagrams focus on database design, UML (Unified Modeling Language) focuses on classes in the system design.
- **Database schema:** The logical structure of a database that defines tables (or collections), columns (or fields), data types, relationships, and constraints. SQL databases have a fixed or strict schema. NoSQL databases usually have a flexible schema or no schema.
- **Entity Relationship:** Logical connection between data entities in a relational database. Eg.: One to one, One to many, Many to many. **ER diagrams** are a visual representation of how entities (a real world object or concept) relate to each other. Various tools and software are available to create ER diagrams.
- **Design flow:** Requirements => Entities => Keys => Relationships => ER Diagram => Normalization => Implementation
  - *Correction:* the notes had Normalization before the ER diagram. In practice you draw the ER diagram first, then normalize the resulting tables.
- **Seeding the database:** Populating the database with some initial dummy data to have some data to work with during development.

**Data modeling process (added)**

1. Requirements: what data, and what are the access patterns (reads vs writes, hot queries)
2. Entities and attributes
3. Relationships: 1:1, 1:N, M:N
4. Keys: primary, foreign, composite, natural vs surrogate (UUID vs auto-increment)
5. Normalize to 3NF, then denormalize only where a measured read path needs it
6. ER diagram, then implementation

**Schema design decisions (added)**

- **SQL:** data types, constraints (NOT NULL, UNIQUE, CHECK, FK), junction tables for many-to-many, index choices, soft vs hard delete, timestamp and audit columns
- **Mongo:** embed vs reference, bounded vs unbounded arrays, 16 MB document limit, deliberate duplication, validation rules
- **Key difference:** SQL = model the data first, then write queries. Mongo = model for the queries (access patterns first).

## 8. SQL vs NoSQL at a glance (added)

|  | SQL (relational) | MongoDB (document) |
| --- | --- | --- |
| Unit of data | Row in a table | Document in a collection |
| Schema | Enforced by the database | Flexible, optional validation |
| Relationships | Joins | Embed or reference, $lookup |
| Scaling | Vertical first, read replicas, sharding is harder | Built-in sharding |
| Transactions | Default way of working | Supported, but costly, design to avoid them |
| Pick when | Integrity, complex joins, reporting | Flexible shape, high write scale, nested data |
