# 1. AUTHENTICATION (AuthN)

## Definition

**Authentication: Who are you?**

- Verifying the user's identity by checking their credentials.
- Is the username and password combination correct?
- Should the user be allowed to log in?
- Authentication verifies that the user is who they claim to be.

## Authentication Methods

### 1. Session-based Authentication

- Server verifies user credentials and creates a session.
- A unique Session ID is generated and stored on the server.
- Session ID is sent to the client, usually inside a cookie.
- The session is used to identify the authenticated user on subsequent requests.

### 2. JWT-based Authentication

- JWT (JSON Web Token) is a token format used to securely transmit information between parties.
- After successful login, the server issues a JWT.
- The client sends the token with subsequent API requests.
- The server validates the token before allowing access to protected resources.

**JWT Structure:**

- Header
- Payload
- Signature

### 3. OpenID Connect (OIDC) Based Authentication

- OIDC is an authentication layer built on top of OAuth 2.0.
- It is used for authentication through a third-party Identity Provider (IdP).
- Examples: Google, Microsoft Entra ID, Okta, Auth0, Keycloak.

### 4. OAuth 2.0

- OAuth 2.0 is an authorization framework.
- It allows an application to access protected resources on behalf of a user.
- OAuth 2.0 provides access tokens.
- OIDC adds the authentication layer and defines the ID Token.

### 5. SSO (Single Sign-On)

- Allows users to log in once and access multiple applications without logging in separately to each application.
- Commonly implemented using protocols such as OIDC and SAML.

### Identity Providers and Services

- Okta
- Amazon Cognito
- Microsoft Entra ID (formerly Azure AD)
- Google
- Auth0
- Keycloak

## Tokens

### 1. ID Token (JWT)

- Contains information about the authenticated user.
- Used by the client application to establish the user's identity.
- Defined by OpenID Connect.

### 2. Access Token

- Used to access protected APIs and resources.
- Sent along with API requests.
- Can be a JWT or an opaque token.

### 3. Refresh Token

- Used to obtain a new access token without requiring the user to log in again.
- Usually has a longer lifetime than an access token.
- Should be stored securely.

**Note:** Access Token, ID Token and Refresh Token serve different purposes.

## Authentication Features

1. **Sign in:** Existing users can log in to the application.
2. **Sign up:** New users can register.
3. **CAPTCHA:** Verify if the user is a human. Example: Select street lights from an image.
4. **Unique username:** Username should be unique at the time of registration. Display a message such as "Username is already taken".
5. **Email verification:** Verify the user's email address.
6. **Phone number verification:** Verify the user's phone number using OTP.
7. **Third-party signup/signin:** Signup or sign in using Google, Facebook, etc., or using email.
8. **Guest login:** Allow users to access the application without creating an account.
9. **Login using OTP:** Allow users to log in using a One-Time Password.
10. **Auto login:** Automatically authenticate the user using an existing valid session or refresh token.
11. **Passwordless sign-in:** Allow users to log in without entering a password.
12. **MFA / 2FA:** Multi-Factor Authentication / Two-Factor Authentication using multiple verification factors such as OTP, authenticator apps or hardware devices.
13. **Active Directory (AD) login:** Allow users to log in using organizational Active Directory credentials.
14. **Password confirmation:** Ask users to enter their password again during registration or sensitive operations.
15. **Change password:** Allow users to change their existing password.
16. **Forgot / Reset password:** Allow users to reset their password when they forget it.
17. **Remember me / Stay signed in:** Keep the user logged in even after closing the tab or browser by maintaining a persistent session.
18. **Store password:** Allow the browser's password manager to save and autofill passwords.
19. **Passkeys:** Passwordless authentication using public-key cryptography. Users can authenticate using biometrics, device PIN or a security key.
20. **Authenticator app:** Allow users to generate OTPs using authenticator applications such as Google Authenticator or Microsoft Authenticator. Commonly uses TOTP (Time-Based One-Time Password).
21. **Recovery codes:** Backup codes that users can use to regain access to their accounts when their primary MFA method is unavailable.

# 2. AUTHORIZATION (AuthZ)

## Definition

**Authorization: What can you do?**

- Determine which parts of the application the user can access based on their role (user/admin).
- Is the user authorized to access this particular part of the product?
- What actions can the user perform after logging in?
- Access to product features and resources is given based on the user's roles and permissions.

## How Authorization Works

- Roles and permissions can be stored in the database and/or included in a JWT token.
- The token is passed along with API requests.
- The backend validates the token and checks whether the user has the required permissions.
- Access to product features and resources is given based on the user's roles and permissions.
- The frontend can show/hide screens and actions based on permissions, but the backend must independently enforce authorization.

## RBAC (Role-Based Access Control)

- Role-Based Access Control: Assign roles and permissions to users so that certain parts of the software are accessible only to certain users.
- Example: Admin, Employee, Manager, User.
- Roles are collections of multiple permissions.
- A user can have one or more roles assigned and through those roles inherit the associated permissions.
- Permissions can be defined for Create, Read, Update and Delete (CRUD) operations on a resource.
- Role and permission information can be received in an API response.
- Based on the permissions in the response, we can show/hide screens or allow/deny actions to users on a screen.
- The backend must also check permissions before allowing the requested operation.

### Example

| Role     | Permissions                  |
| -------- | ---------------------------- |
| Admin    | Create, Read, Update, Delete |
| Manager  | Create, Read, Update         |
| Employee | Read                         |

## Types of Authorization

### 1. Role-Based Access Control (RBAC)

Access is determined based on the user's assigned role.

### 2. Permission-Based Access Control

Access is determined based on specific permissions assigned to the user.

Example:

- user:create
- user:read
- user:update
- user:delete

### 3. Resource-Based Access Control

Access is determined based on the particular resource the user wants to access.

Example: A user can view or edit only their own profile or documents.

### 4. Subscription-Based Authorization

Access is determined based on the user's subscription or purchased plan.

Example:

Suppose there is a software application which has some premium features that are paid.

- Some users will buy the premium subscription.
- Some users will not buy it.
- Based on the user's subscription type, we must determine if the user is authorized to use a particular feature of the application.

## Why Do We Need Authentication and Authorization?

- To protect our APIs.
- To control the access which a user gets to the application.
- To prevent unauthorized users from accessing the application.
- To ensure authenticated users can access only the resources and perform only the actions they are permitted to.

## Authentication vs Authorization

| Authentication          | Authorization                    |
| ----------------------- | -------------------------------- |
| Who are you?            | What can you do?                 |
| Verifies user identity. | Determines user permissions.     |
| Happens first.          | Happens after authentication.    |
| Example: Login.         | Example: Admin can delete users. |

### Authentication and Authorization Approaches

1\. JWT-based Authentication + RBAC (Authorization)

- JWT is used as a token format to authenticate users and carry relevant claims.
- RBAC determines what resources and actions the authenticated user can access.
- Roles and permissions can be included in JWT claims or retrieved from the database.

2\. OpenID Connect (OIDC) (Authentication) + OAuth 2.0 (Authorization)

- OIDC is an authentication layer built on top of OAuth 2.0.
- OIDC is used to authenticate users and obtain their identity information through an ID Token.
- OAuth 2.0 provides access tokens to access protected resources.
- Authorization decisions can be implemented using RBAC, permissions or other access-control mechanisms.

### One important distinction

JWT and OAuth 2.0 are not competing alternatives.

- JWT = Token format.
- OAuth 2.0 = Authorization framework.
- OIDC = Authentication protocol built on OAuth 2.0.
- RBAC = Authorization model.

# 3. SESSIONS AND COOKIES

## Cookies

- Cookies are small pieces of data stored in the user's web browser by a website.
- Stored on the client side.
- Cookies can store information such as session IDs and, in some implementations, authentication tokens.
- Sensitive cookies must be protected using appropriate security attributes.
- Have an expiry period (minutes, hours, days or months).
- A session ID is often stored in a cookie and is sent to the server with applicable requests.

### Cookie Attributes

1. **HttpOnly:** Prevents JavaScript from accessing the cookie.
2. **Secure:** Cookie is sent only over HTTPS.
3. **SameSite:** Controls whether cookies are sent with cross-site requests. Helps protect against CSRF.
4. **Expires / Max-Age:** Defines the cookie's expiry period.
5. **Domain / Path:** Determines where the cookie is sent.

## Sessions

- Sessions store user-related session data on the server side, making them suitable for maintaining sensitive authentication state.
- The user is identified by a Session ID.
- The Session ID is usually stored in a cookie on the client.
- Session data exists until it expires, is invalidated or the user logs out.
- Sessions are commonly used for authentication, and the authenticated identity is then used for authorization checks.

## How Session-based Authentication Works?

1. **User Login:** Server verifies the user's credentials and creates a session.
2. **Session Creation:** A unique Session ID is generated and the actual session data is stored on the server.
3. **Set-Cookie:** Session ID is sent to the client inside the Set-Cookie HTTP response header.
4. **Cookie Storage:** Browser stores the cookie.
5. **Subsequent API Requests:** Browser automatically sends the cookie with applicable requests.
6. **Session Validation:** Server checks the Session ID against the session stored on the server.
7. **Authorization:** Server identifies the user and performs authorization checks.
8. **Logout:** Server invalidates or clears the session, and the browser cookie is cleared or expires.

## Security and Session Management Features

1. **Login API Rate Limiting:** Prevent brute-force attacks where passwords are systematically guessed.
2. **Account Lockout:** Lock the account after a certain number of unsuccessful login attempts. Example: Wrong username or password entered four times. Display a message such as "Account locked due to multiple failed login attempts. Please check your email".
3. **Password Expiry:** Password expires after a particular time duration and the user has to set a new password.
4. **Prevent Password Reuse:** Don't allow the user to reuse old passwords, according to the configured password policy.
5. **Auto Logout:** Automatically log out the user after a certain number of days, session expiry or a few hours of inactivity.
6. **Logout of All Devices:** Allow the user to invalidate sessions on all logged-in devices.
7. **Cookie Consent:** Accept, Accept Essential, Reject All. Used for managing cookie consent and privacy preferences.
8. **HTTPS / SSL (TLS):** Use HTTPS to encrypt communication between the browser and server, protecting credentials, cookies and tokens during transmission.
9. **Single-Device Login:** User can use the application on only one machine at a time. If the user logs in with the same credentials on another machine, the previous session can be invalidated.
10. **Concurrent Login Restriction:** Detect if multiple devices or users are sharing credentials for a premium account, like Netflix. Depending on the application's policy, block or terminate simultaneous sessions.

## Other Important Security Concepts

- **Password Hashing:** Passwords should never be stored in plain text. Use secure password hashing algorithms such as bcrypt or Argon2.
- **XSS (Cross-Site Scripting):** An attack where malicious scripts are injected into a website. Can be used to steal accessible tokens or compromise user sessions.
- **CSRF (Cross-Site Request Forgery):** An attack where an authenticated user's browser is tricked into making unwanted requests.
- **CORS (Cross-Origin Resource Sharing):** Browser security mechanism that controls which origins can access resources from another origin.
- **401 Unauthorized:** User is not authenticated or valid authentication credentials are missing/invalid.
- **403 Forbidden:** User is authenticated but does not have permission to perform the requested action.
