## 1. Backend engineering - First principles

### What a backend does?

- It receives a request, checks who is calling, validates the input, runs business logic, reads or writes data, and returns a response.
- Everything else in this doc (caching, queues, load balancers, gateways) exists to make that loop faster, safer, or able to handle more load.

### Client-server and statelessness

- The client sends a request and the server sends a response. That is the whole model.
- HTTP is stateless. Each request is independent, and the server does not remember the previous one.
- Anything that must be remembered (a login, a cart) is kept somewhere outside the request: a database, a cache, a session store, or a token like a JWT.

### State: where it lives

- State can live in server memory, in a database, in a cache, or in the client (token, cookie).
- If state lives in one server's memory, you cannot freely add more servers. Requests landing on a different server will not find it.
- Keep servers stateless and put state in shared stores. This is what makes horizontal scaling, load balancing and autoscaling possible.

### Concurrency

- A server gets many requests at the same time. There are two common ways to handle that: one thread per request, or an event loop.
- Node uses an event loop on one main thread with non-blocking I/O. It is excellent for I/O-bound work (database calls, API calls, file reads).
- CPU-bound work (image processing, heavy loops) blocks the event loop. Move it to worker threads, child processes, or a queue.

### Data

- Persistence: data must survive a restart, so it goes to a database.
- Transactions: a group of operations that succeed or fail together (ACID: atomicity, consistency, isolation, durability).
- Indexes make reads fast and writes slower. Normalization reduces duplication, and denormalization trades it for faster reads.
- Consistency: after a write, does every reader see it immediately (strong) or only eventually?

### Failure

- Networks, databases and other services fail, and the failure is partial and random, not rare.
- Use timeouts so a slow dependency does not hang your server. Use retries with backoff for temporary failures.
- Make operations idempotent (safe to repeat), so a retry does not create a duplicate order or payment.
- Return meaningful errors with the right status codes, and log enough to trace what happened.

### Trade-offs

- Latency (time for one request) vs throughput (requests per second).
- Vertical scaling (bigger machine) vs horizontal scaling (more machines).
- Consistency vs availability when a network partition happens (CAP theorem).
- A cache makes reads fast but can serve stale data. A queue makes a request fast but moves the work to later.
- There is no free option. Every concept below is a trade-off.

### Where each concept fits

| Problem                                            | Concept that solves it                           |
| -------------------------------------------------- | ------------------------------------------------ |
| One client sends too many requests                 | Rate limiting                                    |
| One server is overloaded                           | Load balancing, autoscaling                      |
| The same data is read again and again              | Caching, CDN                                     |
| The database is slow                               | Indexing, query optimization, replicas, sharding |
| Work inside a request takes too long               | Message queues, background jobs                  |
| The system has grown too large for one codebase    | Microservices, API gateway                       |
| Another system must be told when something happens | Webhooks, event-driven architecture              |
| Client should not reach servers directly           | Proxy, reverse proxy                             |

## 2. Backend concepts

1. Rate limiting : A way to control the number of requests a client (like a user, app or system) can make to a server within a specific period.
2. Load balancing : A way to distribute incoming requests or traffic across multiple servers to ensure no single server gets overloaded.
3. Auto Scaling: A mechanism that automatically increases or decreases the number of server instances based on traffic or resource usage (CPU, memory, requests).
4. Caching : A way to store frequently accessed data temporarily so that it can be retrieved quickly without repeatedly fetching it from original source.
5. CDN : A network of servers distributed across different locations that work together to deliver content to users more quickly.
6. Microservices : An architectural style where an application is divided into smaller, independent services, each responsible for a specific piece of functionality.
7. API Gateway : A server that acts as an entry point for all client requests to your system. It routes those request to the appropriate microservice, handles load balancing and other tasks. The other tasks usually include authentication, rate limiting and logging.
8. Webhooks : A way for one application to send real-time updates or notifications to another application when a specific event happens.
9. Sharding : Method of splitting large database into smaller, more manageable pieces called shards.
10. Proxy : Server that acts as an intermediary between client (like browser) and another server (like a website). A forward proxy sits in front of clients (hides the client from the server). A reverse proxy sits in front of servers (hides the servers from the client). Nginx is commonly used as a reverse proxy.
11. Message Queues : System used to send, store and retrieve messages between different parts of an application (or between applications) in a reliable and organized way.
12. Backend consists of a physical server hardware instance and server software like nginx, apache, tomcat, IIS etc. A backend is also the application code and the database, not only the hardware and server software.
13. Contract API/ Mock API: A **mock API** is a simulated API that returns predefined responses, used for development and testing before the real backend is ready. A **contract** (API contract) is the agreed specification of endpoints, request and response formats, usually written in OpenAPI. Frontend and backend build against the contract, and a mock is often generated from it.
14. API Design doc: A detailed specification describing API endpoints, request/response formats, authentication, error handling, and usage guidelines.

## 3. System design

### LLD: Low Level Design

SOLID Principles

- **S** Single Responsibility: a class or module has one reason to change.
- **O** Open/Closed: open for extension, closed for modification.
- **L** Liskov Substitution: a subclass can replace its parent without breaking behavior.
- **I** Interface Segregation: many small interfaces are better than one big one.
- **D** Dependency Inversion: depend on abstractions, not concrete classes.

Design patterns: Common ones: Singleton, Factory, Observer, Strategy, Repository, MVC.

---

### HLD: High Level Design

Typical components of a system:

1. API Gateway: Single entry point. Routes requests, handles auth and rate limiting.
2. Reverse proxy: Sits in front of servers and forwards client requests to them (Nginx).
3. Load balancer: Spreads requests across server instances.
4. High availability: No single point of failure. Run more than one instance of everything important.
5. Autoscaling group: Adds or removes server instances based on load.
6. Server instances: The machines or containers that run your application.
7. Database: Persistent storage, often with replicas for reads and backups.
8. Cache: Fast in-memory store (Redis) for frequently read data.
9. CDN: Serves static content from locations close to the user.
10. Microservice: A small independent service that owns one piece of functionality.
