# ENCRYPTION & CRYPTOGRAPHY

## 1. Types of Encryption

Symmetric Encryption

- Same key is used for both encryption and decryption.
- The sender and receiver must securely share the encryption key.

Asymmetric Encryption

- Uses two keys: Public key and Private key.
- Each party has its own public-private key pair.
- Public key can be shared, but private key must never be shared.

Examples: RSA (Rivest–Shamir–Adleman).

## 2. Asymmetric Encryption

- Asymmetric encryption uses public and private keys.
- Both sender and receiver have their own public-private key pair.
- Private key is not shared with anyone. Public key can be shared.
- Once a connection is established between sender and receiver, their public keys can be exchanged.
- Public keys can be stored in public key servers, directories, websites, repositories, embedded in email signatures, or shared directly.

### Encryption and Decryption

Receiver:

- Public key – Encrypt
- Private key – Decrypt

Sender:

- Private key – Sign
- Public key – Verify

| Operation                 | Key used               |
| ------------------------- | ---------------------- |
| Encrypt data for receiver | Receiver's public key  |
| Decrypt received data     | Receiver's private key |
| Create digital signature  | Sender's private key   |
| Verify digital signature  | Sender's public key    |

### Asymmetric encryption workflow

When the sender wants to send an encrypted and digitally signed file to the receiver:

1. Sign (Private Key – Sender): Create a digital signature using the sender's private key.
2. Encrypt (Public Key – Receiver): Encrypt the data and digital signature using the receiver's public key.
3. Send File: Send the encrypted file to the receiver.
4. Decrypt (Private Key – Receiver): Receiver decrypts the file using their private key.
5. Verify (Public Key – Sender): Receiver verifies the digital signature using the sender's public key.

- Sign (Private Key - Sender) => Encrypt (Public Key - Receiver) => Send File => Decrypt (Private Key - Receiver) => Verify (Public Key - Sender)
- Source: Sign + Encrypt.
- Destination: Decrypt + Verify.

Note: Signing and encryption are separate operations. The exact implementation depends on the cryptographic protocol. The above describes the overall workflow.

Examples:

- PGP – Pretty Good Privacy.
- GPG – GNU Privacy Guard.

### Storage of Keys

1\. Private keys:

- On device.
- Hardware tokens.

2\. Public keys:

- Public key servers.
- Directories.
- Websites.
- Repositories.
- Embedded in email signatures.
- Direct sharing.

## 3. Digital Signatures

### What is Digital Signing?

- Digital signing is the process of attaching a digital signature to a message or file.
- Pass the data through a hash function to generate a fixed-size fingerprint of the data.
- Sign the generated hash using the sender's private key.
- This creates a digital signature associated with the file.

### SIGN: PRIVATE KEY – SENDER

1. Sender creates a hash of the original data using a hash function.
2. The hash is digitally signed using the sender's private key.
3. The resulting digital signature is attached to the original data.

### ENCRYPT: PUBLIC KEY – RECEIVER

1. Combine the plaintext data and digital signature.
2. Encrypt the data and signature using an encryption algorithm and the receiver's public key.
3. Send the encrypted data to the receiver.

### DECRYPT: PRIVATE KEY – RECEIVER

- Opposite of encryption.
- Receiver uses their private key to decrypt the received data.
- This recovers the original plaintext and digital signature.

### VERIFY: PUBLIC KEY – SENDER

- Opposite of signing, conceptually.
- Receiver uses the sender's public key to verify the digital signature.
- The receiver independently calculates the hash of the received data and checks it against the hash authenticated by the signature.

Digital signatures provide:

- Authenticity: Verify the sender's identity, provided the public key is reliably associated with that sender.
- Integrity: Ensure the file or message has not been tampered with.
- Non-repudiation: Provides cryptographic evidence that the holder of the private key signed the data. This depends on proper key protection and identity management.

### Quick Revision

- Sender: Private key – Signing, Public key – Verification.
- Receiver: Private key – Decryption, Public key – Encryption.
- Public key - **Encrypt** data or **verify** a signature
- Private key - **Decrypt** data or **create** a signature

Example: RSA (Rivest–Shamir–Adleman) is an asymmetric cryptographic algorithm that supports encryption and digital signatures.

## 4. Cryptographic Keys

### What is a Cryptographic Key?

- A sequence of characters or bits used by a cryptographic algorithm to transform or protect sensitive data.
- Data before encryption is called plaintext.
- Encrypted data is called ciphertext.

Plaintext + Key = Ciphertext

### Key Rotation

- Replacing an existing key by generating or introducing a new key.
- It is used to limit the amount of data encrypted by a single key and reduce the impact of key compromise.
- Something like changing the password of your account after a fixed number of months.

## 5. Hashing and Salting

### Hashing

- Hashing is a one-way process that converts data into a fixed-length hash using hash functions or algorithms.
- It creates a fixed-length string or hash (digest).
- Hashes are designed to be one-way. They cannot feasibly be transformed back into the original plaintext.
- Even a tiny change in a file or data produces a significantly different hash. This is useful to check whether data has been tampered with.
- Hashing is not encryption. It does not use an encryption key and does not produce ciphertext.

Password Hashing:

- Server should never store plaintext passwords. It stores salted password hashes.
- While logging in, the server processes the entered password using the same password-hashing algorithm and stored salt.
- It then compares the resulting hash with the stored hash.
- If they match, the user is authenticated successfully.

Passwords should be stored using purpose-built password-hashing algorithms such as Argon2id, bcrypt or scrypt, not ordinary fast hash functions such as SHA-256.

### Salting

- Adding a random sequence of characters, called a salt, to a password before hashing.
- Just like we add salt to food to enhance its taste, we salt a password to make password hashing more secure.
- After salting, the password is hashed.
- A unique salt should be generated for every password.
- The salt is stored alongside the password hash. It does not need to be secret.

### Hash-based Message Authentication Code (HMAC)

- HMAC stands for Hash-based Message Authentication Code.
- It uses a cryptographic hash function along with a secret key.
- It is used to verify data integrity and authenticity.
- Unlike a digital signature, HMAC uses a shared secret key. Both sender and receiver must know that secret key.
- Anyone possessing the shared key can generate and verify an HMAC.

### SSE-C and HMAC

- SSE-C stands for Server-Side Encryption with Customer-Provided Keys.
- In AWS S3 SSE-C, the customer provides the encryption key with each request.
- S3 does not store the encryption key.
- S3 stores a randomly salted HMAC-based value of the encryption key (for key verification).
- The stored HMAC value cannot be used to derive the original encryption key or decrypt the contents of the encrypted object.
- That means, if you lose the encryption key, you lose access to the encrypted object.

AWS terminology clarification: S3 uses a salted HMAC-based key-verification value, not a password-style salted password hash. The customer must retain the encryption key.

## 6. Encoding vs Encrypting vs Hashing

### Encoding

- Converting data from one format to another.
- Used to conveniently transfer data across computers in a format that can be easily used by different types of systems.
- Does not use any key. It uses an encoding algorithm.
- Not a security mechanism. Anyone can decode the data using the corresponding decoding algorithm.

Examples:

- ASCII.
- Unicode.
- URL Encoding.
- Base64 Encoding.

### Encrypting

- Used to alter sensitive data in such a way that only an intended party with the appropriate key can understand it, while unintended parties find it meaningless.
- Uses keys and encryption algorithms.
- Provides confidentiality.

Examples:

- RSA.
- AES-256.

### Hashing

- Converts data into a fixed-length hash using a one-way hash function.
- Cannot feasibly be reversed to obtain the original data.
- Used for integrity verification and password storage.

Examples:

- SHA-256.
- SHA-512.

### Quick Comparison

| Feature    | Encoding            | Encryption      | Hashing                  |
| ---------- | ------------------- | --------------- | ------------------------ |
| Purpose    | Data representation | Confidentiality | Integrity / verification |
| Uses key   | No                  | Yes             | Not normally             |
| Reversible | Yes                 | Yes, with key   | No, practically          |
| Example    | Base64              | AES, RSA        | SHA-256                  |

### Scrambling or Randomizing the Data?

- Encryption transforms data into an unintelligible form using a cryptographic algorithm and key.
- The transformation may appear random, but it is not simply randomizing or scrambling data.
- The intended recipient can recover the original data using the appropriate decryption key.

## 7. SSL/TLS and HTTPS

### HTTPS Website

- HTTPS uses TLS (Transport Layer Security) to secure communication between a browser and a web server.
- Older versions of SSL (Secure Sockets Layer) existed, but SSL is deprecated. Modern websites use TLS.
- TLS uses both asymmetric cryptography and symmetric encryption.
- The website's public key is included in its digital certificate.
- The corresponding private key is securely stored on the server.
- The server's public-private key pair is generally generated before the TLS handshake, not during it.

### How TLS Works (High-Level)

1. Browser connects to the website.
2. Browser and server perform a TLS handshake.
3. Server sends its digital certificate containing its public key.
4. Browser verifies the certificate and its trust chain.
5. Browser and server establish shared session keys using a key-establishment mechanism (commonly ephemeral Diffie-Hellman).
6. Both parties use symmetric encryption to secure application data exchanged during the session.

Important:

- Asymmetric cryptography: Used for authentication and key establishment.
- Symmetric encryption: Used for encrypting actual communication data.
- Digital certificates: Used to establish trust in the server's identity.

## 8. Digital Certificates

### What is a Digital Certificate?

- A digital certificate is an electronic document that establishes the association between an identity (such as a website's domain name) and a public key.
- It is used to establish trust and authenticate the identity of a website or entity.
- It contains the public key, subject/domain information, issuer information, validity period, and digital signature of the issuing Certificate Authority.

### Certificate Authority (CA)

- A Certificate Authority is a trusted organization that issues and digitally signs digital certificates.
- The CA verifies the domain or identity according to its certificate issuance process.
- Browsers and operating systems maintain trusted CA certificates.
- The browser uses this trust information to verify the website's certificate.

### Certificate Verification (High-Level)

1. Website sends its digital certificate to the browser.
2. Browser checks the certificate's validity.
3. Browser checks whether the domain name matches.
4. Browser verifies the CA's digital signature.
5. Browser checks the certificate chain up to a trusted root CA.
6. Browser checks certificate expiration and other relevant constraints.
7. If verification succeeds, the browser can establish a trusted TLS connection.

### Certificate Chain

- A certificate chain establishes trust between the website certificate and a trusted root CA.
- It generally consists of:
  1. Server/website certificate.
  2. Intermediate CA certificate.
  3. Root CA certificate.

### Certificate Expiration

- Every digital certificate has a validity period.
- Once a certificate expires, it must be renewed or replaced.
- An expired certificate can cause browsers to display security warnings and reject or distrust the connection.

## 10. AWS Encryption References

| AWS concept | Meaning                                            |
| ----------- | -------------------------------------------------- |
| SSE-S3      | Server-Side Encryption with Amazon S3 managed keys |
| SSE-KMS     | Server-Side Encryption with AWS KMS keys           |
| SSE-C       | Server-Side Encryption with Customer-Provided Keys |

- SSE-S3: S3 manages the encryption keys.
- SSE-KMS: AWS Key Management Service manages the keys and provides additional key-management controls.
- SSE-C: Customer provides and manages the encryption key. S3 does not store the key.

One important distinction to retain throughout these notes:

- Encryption → Confidentiality.
- Hashing → One-way transformation and integrity checking.
- Digital signature → Authenticity and integrity.
- HMAC → Integrity and authenticity using a shared secret.
- Encoding → Data representation.
- Digital certificate → Binds an identity to a public key.
