**API:**

- API: Application Programming Interface. Two applications run programs, maybe in the same or different programming languages. The way they exchange data with each other is in the form of an interface.
- The two applications may be a frontend (JavaScript) and a backend (Java, C#) etc. Or it may be a server which has some data and we consume it for information. Or some framework/library which exposes built-in functions, where we use only its public, documented surface without knowing its internals.

---

**HTTP METHODS:**

1. GET: Gets data to client. Can be list of resources or details of a resource
2. POST: Creates a resource
3. PUT: Updates the entire resource in the DB, it overrides the existing data.
4. PATCH: Updates a part of resource, a small patch.
5. DELETE: Deletes a resource.
6. HEAD: Same as GET, but returns only headers (no response body).
7. OPTIONS: Returns supported HTTP methods for a resource. Used heavily in CORS.
8. QUERY: (New) Like GET, but it allows a request body, so it suits complex searches that don't fit in a URL. It is new and still being standardized, so support is limited. Verify before relying on it.

Input types:

- Query parameters: query parameter after question mark - key and value. Starts with a ? and seperated key value pairs by &. localhost:3000?name=John&surname=Watson&age=25
- Path parameters: string interpolation in the URL. Eg: getdata/{product}/{id}
- Request body: Pass an object

---

**HTTP STATUS CODES:**

2xx — Success

- **200 OK** – Request succeeded (the most common one).
- **201 Created** – Resource successfully created (common in POST requests).
- **202 Accepted** – Request accepted, processing happens later (async jobs).
- **204 No Content** – Success, but no response body (often used for DELETE).

3xx — Redirection

- **301 Moved Permanently** – Resource has a new permanent URL.
- **302 Found** – Temporary redirect (very common on the web).
- **304 Not Modified** – Cached version is still valid (huge for performance).

4xx — Client Errors

- **400 Bad Request** – Malformed or invalid request.
- **401 Unauthorized** – Authentication required or failed. “who are you?”
- **403 Forbidden** – Authenticated, but not allowed. “I know who you are, but no”.
- **404 Not Found** – Resource doesn’t exist (iconic).
- **405 Method Not Allowed** – HTTP method not supported.
- **409 Conflict** – Request conflicts with current state (e.g., duplicate data).
- **429 Too Many Requests** – Rate limit exceeded.

5xx — Server Errors

- **500 Internal Server Error** – Generic server failure.
- **502 Bad Gateway** – Invalid response from upstream server.
- **503 Service Unavailable** – Server overloaded or down.
- **504 Gateway Timeout** – Upstream server didn’t respond in time.

---

**HTTP HEADERS:**

1] Request headers:

- Host: Target server
- Authorization: Contains the JWT token. It carries credentials, usually in the form `Bearer <token>`.
- Content type: Format of request body
- Origin: Origin of cross-origin request
- Cookie: Session cookies
- Accept (format the client wants back), User-Agent (client details)

2] Response headers:

- Access-Control-Allow-Origin
- Content-Security-Policy
- Content-Type, Set-Cookie, Cache-Control, Location (used with redirects)

These are few typical

**API FEATURES:**

- Search, Sort, Filter, Pagination
- Technical errors and exceptions should be mapped to meaningful user understandable response messages.
- Schema validation
- Versioning: Use the words - 'api/v1/....' while creating API endpoints
- API layer: Group of APIs
- API can send a json response or HTML response. HTML response is SSR.
- cURL commands: A command-line tool to call an API.

Example:

```Shell
curl -X POST http://localhost:3000/api/v1/products \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <token>" \
  -d '{"name": "Phone", "price": 500}'
```

---

**HTTP API vs REST API:**

- HTTP API is an API which uses HTTP/HTTPS protocol.
- REST : REpresentational State Transfer. Its an architectural style, a set of constraints for designing API.
- REST API works in Client-Server architecture. All operations in REST API are stateless.
- Stateless: every request carries everything the server needs. The server keeps no client session between requests.
- REST constraints: client-server, stateless, cacheable, uniform interface, layered system. Code on demand is optional.
- Common conventions: nouns in URLs (`/users/5`, not `/getUser`), HTTP methods for the action, proper status codes.

- You need a postman collection or Swagger documentation to write the code and write some ajax requests etc.

```JavaScript
const response = await fetch("http://localhost:3000/api/v1/products", {
method: "POST",
headers: {
"Content-Type": "application/json",
Authorization: Bearer ${token},
},
body: JSON.stringify({ name: "Phone", price: 500 }),
});
const data = await response.json();
```

**API Producer and Consumer:**

- Producer: the app that exposes the API (the backend).
- Consumer: the app that calls it (the frontend or another service).
- Publisher(something which sends messages or events) and subscriber(something which receives the ones it subscribed to). A publisher sends messages or events, and a subscriber receives them. This is the pub/sub pattern used with message queues. It is a different idea from API producer and consumer.
