## Part 05: Connecting Bitbucket to Jenkins — adding the Bitbucket PAT in Jenkins credentials

1. **In Bitbucket:** Manage account → Personal access tokens → Create token.
   - Name: purpose-specific (e.g. `jenkins-vm-learning-readonly`), not a reused personal token.
   - Permissions: **Repository Read** + **Project Read** only — scoped to the minimum needed for Jenkins to clone.
2. **In Jenkins:** Manage Jenkins → Credentials → System → Global credentials → Add Credentials.
   - Kind: **Username with password**
   - Username: the actual Bitbucket account username (not the credential's own ID — easy mistake to make).
   - Password: the PAT value.
   - ID: a memorable name, e.g. `bitbucket-creds`.
3. Selected this credential in the Pipeline job's SCM configuration (Part 04).

**Security principle used:** never reuse a broad, already-in-use personal token for a CI system — always mint a new, narrowly-scoped, purpose-named credential. This limits blast radius and keeps revocation clean.

## Part 06: Connecting Jenkins to Bitbucket — creating a webhook (attempted)

Goal: trigger builds automatically the instant a push happens, instead of manually or via polling. Since Bitbucket here is an **internal Server/Data Center** instance (not public Cloud), a real webhook seemed plausible — traffic never leaves the org network.

**Steps taken:**

1. Installed the **Bitbucket Server Integration** plugin in Jenkins (Manage Jenkins → Plugins).
2. In the Pipeline job's **Build Triggers**, enabled **"Bitbucket webhook trigger"** with **Push event**.
3. In Bitbucket → repo → Repository settings → Webhooks, added a webhook:
   - URL: `http://<Your VM IP>:8080/bitbucket-hook/`
   - Event: Repository push
4. Used Bitbucket's **Test Connection** button to validate inbound reachability.

**Outcome:** the webhook call consistently failed with `403 — No valid crumb was included in the request` — a Jenkins CSRF/crumb protection issue, not a network/firewall problem (inbound connectivity itself worked fine). This turned out to be a plugin/Jenkins-core version compatibility gap rather than a misconfiguration on our end. The only remaining fix (disabling CSRF protection instance-wide) was judged too broad a security tradeoff for a shared VM, so the webhook was **not used** — see Part 07 for the working alternative.

_(Full diagnostic trail — including the API-token/permission red herrings along the way — is documented in `3. Jenkins.md`, Section 6.23, for reference.)_

# Concepts

## 01. Nginx

**What it is:** a web server — listens on a port and serves files or proxies requests. Excellent at serving static files (HTML/CSS/JS) efficiently, and commonly used as a reverse proxy in front of application servers.

**Is it required?** No — alternatives exist (`npx serve`, Apache, Caddy, IIS). But it's the standard, most efficient choice for serving a built frontend app.

**Important distinction:** Nginx is _not_ a "backend"/application server. It doesn't execute code or talk to databases — it just hands out static files exactly as they exist on disk. The React app itself only actually _runs_ once it reaches the browser; Nginx is purely the delivery mechanism.

**Basic config concept — a "server block":**

```nginx
server {
    listen 8081;                        # port to listen on
    server_name _;                       # matches any hostname
    root /usr/share/nginx/react-app;     # docroot — where the static files live
    index index.html;                    # default file to serve
    location / {
        try_files $uri $uri/ /index.html;   # needed for SPA client-side routing
    }
}
```

Multiple server blocks can coexist on different ports without interfering — this is how we kept our app isolated from Nginx's default site.

## 03. Jenkinsfile & Declarative Pipeline

A **Jenkinsfile** is a text file (checked into the repo) defining the entire build/test/deploy process as code, instead of configuring it by hand through the Jenkins UI. Declarative pipelines follow a fixed structure:

```groovy
pipeline {
    agent any              // where to run (any available executor)
    tools { ... }           // tools Jenkins should provision (e.g. a specific NodeJS version)
    environment { ... }     // environment variables available to all stages
    stages {
        stage('Name') {
            steps { ... }    // shell commands / actions for this stage
            when { ... }      // conditional execution (e.g. only on a specific branch)
        }
    }
    post { ... }            // actions after the pipeline finishes (success/failure)
}
```

**Multibranch vs single Pipeline job:** `when { branch 'x' }` conditions only auto-work with a **Multibranch Pipeline** job, which sets the `BRANCH_NAME` variable automatically per branch. A plain single Pipeline job (what we built) doesn't set this automatically — we manually set `BRANCH_NAME = 'main'` in the `environment {}` block as a workaround, since only one branch (`main`) exists today.

---

## 04. Jenkins Credentials

Jenkins stores secrets (passwords, tokens, SSH keys) in an encrypted credential store, referenced by an **ID** (not the secret value itself) inside pipeline/job configuration — this keeps secrets out of the Jenkinsfile/source code.

**Key distinction learned the hard way:** a credential's **ID** (e.g. `bitbucket-creds`, used internally by Jenkins to reference the credential) is a completely different field from its **Username** (the actual account name sent to the remote server). Mixing these up causes silent authentication failures that look like a bad password/token, when the real issue is a wrong field.

**Best practice:** mint narrowly-scoped, purpose-named credentials for CI use (e.g. a repository-read-only token) rather than reusing a broad personal token — smaller blast radius, cleanly revocable without affecting real work.

## 05. CSRF Protection & Jenkins "Crumb"

Jenkins includes CSRF (Cross-Site Request Forgery) protection by default — it requires a **crumb** (a per-session security token) on most requests to prevent malicious sites from triggering actions using an already-logged-in browser session.

**Why this matters for webhooks:** an external system (like Bitbucket) calling Jenkins doesn't have a browser session or a crumb — so plugins that handle webhooks (GitHub plugin, Bitbucket Server Integration plugin) are expected to register their own dedicated endpoint that's explicitly exempted from crumb checks (a `CrumbExclusion`). If a plugin's exemption doesn't work correctly (e.g., due to a version mismatch with Jenkins core), webhook calls get rejected with `403 No valid crumb was included in the request`, even with valid authentication.

**Common misconception:** API-token/Basic-Auth requests are **not** automatically exempt from CSRF crumb checks — exemption depends specifically on a registered `CrumbExclusion` for that URL path, not on how the request is authenticated.

**Tradeoff:** Jenkins does allow disabling CSRF protection instance-wide, but this weakens security for the entire instance (any logged-in session becomes vulnerable to being tricked into performing actions), so it should only be considered on a fully personal, non-shared instance — not a shared/org-owned system.

## 06. Deploying to Vercel/Netlify instead of a self-managed server

Rather than deploying to a VM's Nginx docroot, a Jenkinsfile can push the built static site directly to a managed hosting platform — removing the need to run/secure a web server at all:

```groovy
stage('Deploy to Vercel') {
    steps {
        sh 'npx vercel --prod --token=$VERCEL_TOKEN --yes'
    }
}
// or
stage('Deploy to Netlify') {
    steps {
        sh 'npx netlify deploy --prod --dir=dist --auth=$NETLIFY_TOKEN'
    }
}
```

- Requires a free account + a deploy token from Vercel/Netlify, stored as a Jenkins **Secret text** credential.
- Jenkins only needs **outbound** internet access to reach their API — no inbound exposure, no firewall/CSRF complexity, regardless of where Jenkins itself runs.
- This is the "correct" way to get a genuinely public URL for a personal project — using a purpose-built public hosting platform, instead of trying to expose internal/shared infrastructure (which we deliberately avoided doing to the org VM).

## 07. Trigger mechanism strategy: Poll SCM vs. Webhook — a networking-fundamentals view

Any trigger where an external service (GitHub/Bitbucket) needs to reach Jenkins requires **some form of public-facing address** — this is a fundamental property of inbound networking, not a gap in any particular setup. Three ways to resolve it:

1. **Poll SCM** — Jenkins reaches _out_ to the git server on a schedule (e.g. `H/5 * * * *`); no public address ever needed, since the connection direction is reversed. Zero infrastructure dependency, at the cost of a small trigger delay.

   **How polling vs. triggering actually works (confirmed in practice):** with `H/5 * * * *`, Jenkins performs a **poll** (a lightweight "anything new?" check against the repo) roughly **12 times per hour** — but a **build only starts** on the poll(s) where a new commit is actually found since the last check. So seeing just "1 build in the last hour" after pushing one commit is correct behavior, not a bug — polling itself never shows up in build history, only actual detected changes do. The delay between pushing and the build starting is **not a fixed 5 minutes** — it depends on where your commit lands relative to the schedule's fixed polling instants (could be seconds, could be nearly the full interval). The full poll history (including "no changes found" checks) is visible at `http://<Your VM IP>:8080/job/<job-name>/pollLog/`.

2. **Temporary tunnel (ngrok / Cloudflare Tunnel)** — gives a local machine a temporary public HTTPS address, active only while running. No VM/router config needed, but the URL changes each restart (needs re-configuring the webhook each session, unless paying for a static subdomain).
3. **A permanent public address of your own** — the only way to get a stable, always-reachable inbound target; inherently requires some internet-facing infrastructure (a VPS, or a home router with port-forwarding + dynamic DNS).

**Real-world practice isn't one-size-fits-all:**

- Companies using fully-managed SaaS CI (GitHub Actions, GitLab CI) get webhooks natively, no networking work needed — this is the modern trend, and part of why many teams move away from self-hosted Jenkins.
- Self-hosted Jenkins at companies with dedicated infra/network teams commonly use real webhooks (reverse proxies, firewall rules opened for known source-control IP ranges).
- **Poll SCM (or similar pull-based approaches) is standard, not just a fallback, in regulated/air-gapped environments** (banking, healthcare, defense, strict internal policies) where inbound connections from external systems are disallowed as a matter of policy — not a budget/skill gap.

**Takeaway for a personal setup with no stable public address and no dedicated network team:** this is architecturally closer to the "regulated/constrained" bucket than the "well-resourced enterprise" bucket — so Poll SCM is a legitimate, realistic choice for this context, not a lesser workaround. A temporary tunnel (ngrok) remains a reasonable option specifically if the _learning goal_ is to experience real webhook mechanics firsthand.

# Advanced Reference: Realistic Multi-Environment Enterprise Pipeline

This section is a **design reference**, not something implemented on the practice VM — it documents how the concepts above scale up to a realistic enterprise setup with multiple branches, multiple deployment targets, and stricter safety gates.

**Scenario:** a repo with 3 long-lived branches (`main`, `uat`, `production`); a PR merge into any of them should build and deploy to that environment's own VM (different IP/port/credentials per environment).

## Key architectural shifts vs. a simple single-branch/single-VM setup

|               | **Simple setup (our project)**       | **Enterprise scenario**                                                                                                        |
| ------------- | ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| Branches      | Single (`main`)                      | 3 branches:`main` → dev, `uat` → UAT, `production` → prod                                                                      |
| Job type      | Single Pipeline                      | **Multibranch Pipeline** — auto-discovers branches and natively populates `BRANCH_NAME` per branch (no manual override needed) |
| Deploy target | Same VM as Jenkins (local file copy) | **Remote VMs** — SSH-based deploy, different IP/port/credentials per environment                                               |
| Trigger       | Poll SCM                             | Real**webhook** (enterprise infra/network teams maintain the firewall rules and plugin versions that make this reliable)       |
| Credentials   | One shared token                     | **Per-environment** deploy credentials (`dev-vm-ssh`, `uat-vm-ssh`, `prod-vm-ssh`) — never shared across environments          |
| Safety        | N/A                                  | **Manual approval gate before prod** — automated dev/UAT, human-gated production                                               |

## 1. Job type: Multibranch Pipeline

Unlike a single Pipeline job (which only tracks one branch), a **Multibranch Pipeline** job scans the whole repo, automatically creates a sub-job per discovered branch, and — critically — sets the `BRANCH_NAME` environment variable correctly and automatically for each one. This is what makes `when { branch 'x' }` conditions work as intended, without the manual `environment { BRANCH_NAME = 'main' }` workaround our single-Pipeline project needed.

## 2. Per-environment credentials

Create separate, narrowly-scoped Jenkins credentials for each environment — e.g. `dev-vm-ssh`, `uat-vm-ssh`, `prod-vm-ssh` — each only able to reach its own target VM. This follows the same blast-radius principle used for the Bitbucket PAT earlier: never let one credential span multiple environments, especially production.

## 3. Jenkinsfile — branch-aware, parameterized deploy

```groovy
pipeline {
    agent any
    tools { nodejs 'Node22' }

    stages {
        stage('Checkout') { steps { checkout scm } }
        stage('Install')  { steps { sh 'npm ci' } }
        stage('Lint')     { steps { sh 'npm run lint' } }
        stage('Build')    { steps { sh 'npm run build' } }

        stage('Deploy to DEV') {
            when { branch 'main' }
            environment { DEPLOY_CREDS = credentials('dev-vm-ssh') }
            steps {
                sh '''
                    scp -o StrictHostKeyChecking=no -r dist/* \
                        ${DEPLOY_CREDS_USR}@dev.internal.company.com:/var/www/app/
                '''
            }
        }

        stage('Deploy to UAT') {
            when { branch 'uat' }
            environment { DEPLOY_CREDS = credentials('uat-vm-ssh') }
            steps {
                sh '''
                    scp -o StrictHostKeyChecking=no -P 2222 -r dist/* \
                        ${DEPLOY_CREDS_USR}@uat.internal.company.com:/var/www/app/
                '''
            }
        }

        stage('Approval for PROD') {
            when { branch 'production' }
            steps {
                input message: 'Deploy to PRODUCTION?', ok: 'Deploy'
            }
        }

        stage('Deploy to PROD') {
            when { branch 'production' }
            environment { DEPLOY_CREDS = credentials('prod-vm-ssh') }
            steps {
                sh '''
                    scp -o StrictHostKeyChecking=no -P 2022 -r dist/* \
                        ${DEPLOY_CREDS_USR}@prod.internal.company.com:/var/www/app/
                '''
            }
        }
    }

    post {
        success { echo 'Pipeline succeeded!' }
        failure { echo 'Pipeline failed — check console output.' }
    }
}
```

**Key mechanics:**

- `credentials('id')` injects a stored credential as environment variables (`_USR`/`_PSW` suffixes for username/password, or a file path for SSH keys) — Jenkins automatically masks the actual secret value in console logs.
- `when { branch 'x' }` works correctly here because the Multibranch Pipeline job type sets `BRANCH_NAME` natively per branch — no manual override required.
- The `input` step **pauses the pipeline** and waits for a human to click "Deploy" in the Jenkins UI before touching production — the real-world safety gate between automated lower environments and production.
- Different IP/port/path per environment are handled via separate stages here (simple, readable); for many similar environments, an alternative is a single parameterized deploy stage driven by a lookup map keyed on `BRANCH_NAME`.

## 4. Trigger: webhook is realistic here (unlike our personal project)

Enterprise Jenkins instances typically have a **dedicated infra/network team** maintaining firewall rules, reverse proxies, and properly up-to-date plugins — exactly the class of setup where webhooks work reliably (see the Poll SCM vs. Webhook discussion above: it's about infra maturity, not just preference).

**Nuance:** a "PR merged" event is technically **a push to the target branch** once merged — so a standard push-based webhook already covers this case, since the Multibranch Pipeline will pick up the new commit on that branch regardless of whether it arrived via direct push or PR merge. If you need to trigger _only_ on merges (excluding direct pushes to protected branches), look for a distinct "Pull Request Merged" webhook event type, offered separately by some Bitbucket/GitHub configurations.
