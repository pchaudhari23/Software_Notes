# Jenkins Notes

Jenkins is an open-source automation server used for building, testing, and deploying software (CI/CD). It runs jobs/pipelines defined by configuration or code (Jenkinsfile), triggered by events (commits, schedules, webhooks).

---

## 1. Beginner

### 1.1 Install Jenkins and explore dashboard

**Install options:**

- **Windows installer**: download `.msi` from https://www.jenkins.io/download/, run it — installs as a Windows service, runs on `http://localhost:8080`.
- **Docker (recommended for learning, easy to reset):**
  ```powershell
  docker run -d --name jenkins -p 8080:8080 -p 50000:50000 -v jenkins_home:/var/jenkins_home jenkins/jenkins:lts
  ```
- **WAR file**: `java -jar jenkins.war` (needs JDK 11/17 installed).

**First run / unlock:**

1. Visit `http://localhost:8080`.
2. Get initial admin password:
   ```powershell
   docker exec jenkins cat /var/jenkins_home/secrets/initialAdminPassword
   ```
3. Choose **Install suggested plugins** (Git, Pipeline, Credentials Binding, etc.) or select manually.
4. Create the first admin user.

**Dashboard overview:**

- **New Item** — create jobs/pipelines.
- **People** — users.
- **Build History** — past runs.
- **Manage Jenkins** — global config, plugins, credentials, nodes, system logs.
- **My Views** — custom dashboards grouping jobs.

**Installing plugins:**
`Manage Jenkins → Plugins → Available plugins` → search (e.g. "Git", "Pipeline", "Blue Ocean", "Docker Pipeline") → Install → restart if required.

### 1.2 Job/item types

When you click **New Item**, Jenkins offers:

- **Freestyle project** — GUI-configured job (source, build steps, post-build actions). Good for simple tasks, no code.
- **Pipeline** — single job driven by Groovy script (declarative or scripted), can be typed in UI or loaded from a Jenkinsfile in SCM.
- **Multibranch Pipeline** — auto-discovers branches/PRs in a repo, creates a sub-job per branch that has a Jenkinsfile.
- **Folder** — organizational container for other jobs.
- **Organization Folder** — scans an entire GitHub org/Bitbucket project for repos with Jenkinsfiles.
- **Multi-configuration project (matrix)** — runs the same job across a matrix of configurations (e.g. OS x JDK version).

Each type has its own **Configure** page: source code management, build triggers (poll SCM, webhook, cron), build environment, build steps, post-build actions.

### 1.3 Create a basic pipeline and run it

1. **New Item → Pipeline** → name it `hello-pipeline`.
2. Under **Pipeline** section, choose **Definition: Pipeline script**, paste:
   ```groovy
   pipeline {
       agent any
       stages {
           stage('Hello') {
               steps {
                   echo 'Hello, Jenkins!'
               }
           }
           stage('Build') {
               steps {
                   echo 'Simulating a build step...'
               }
           }
       }
   }
   ```
3. **Save** → **Build Now**.
4. Check **Console Output** to see stage-by-stage logs; the **Stage View** shows a visual pipeline graph.

## 2. Credentials & Configuration

Jenkins stores secrets (passwords, tokens, SSH keys, certs) encrypted in its **Credentials** store instead of hardcoding them in jobs.

**Add a credential:**
`Manage Jenkins → Credentials → System → Global credentials (unrestricted) → Add Credentials`

Common kinds:

- **Username with password** — e.g. Git/Docker registry login.
- **Secret text** — e.g. an API token.
- **SSH Username with private key** — for git-over-SSH or remote server deploys.
- **Secret file** — e.g. a `.pem` or `kubeconfig` file.
- **Certificate**.

Give it a memorable **ID** (e.g. `github-creds`, `docker-hub-token`) — you reference this ID in jobs/Jenkinsfiles.

**Using in a Freestyle job:** Configure → "Use secret text(s) or file(s)" build environment option, or reference directly in SCM/source config (e.g. pick the credential in "Git → Credentials" dropdown).

**Using in a Pipeline:**

```groovy
pipeline {
    agent any
    environment {
        DOCKERHUB_CREDS = credentials('docker-hub-token') // exposes DOCKERHUB_CREDS_USR / _PSW
    }
    stages {
        stage('Login') {
            steps {
                sh 'echo $DOCKERHUB_CREDS_PSW | docker login -u $DOCKERHUB_CREDS_USR --password-stdin'
            }
        }
    }
}
```

Or with `withCredentials`:

```groovy
withCredentials([usernamePassword(credentialsId: 'docker-hub-token', usernameVariable: 'USER', passwordVariable: 'PASS')]) {
    sh 'echo $PASS | docker login -u $USER --password-stdin'
}
```

**Other basic configurations** (`Manage Jenkins → System`):

- Global environment variables.
- Number of executors (parallel build slots).
- Configure global tools (JDK, Maven, Git, NodeJS) under **Tools**.
- **Manage Nodes and Clouds** — add agent machines.

## 3. Multibranch Pipeline

A Multibranch Pipeline scans a repository, auto-creates a Jenkins sub-job for **every branch (and PR)** that contains a `Jenkinsfile`, and removes jobs for deleted branches.

**Setup:**

1. **New Item → Multibranch Pipeline** → name it.
2. **Branch Sources → Add source** → Git/GitHub/Bitbucket → repo URL + credentials.
3. **Build Configuration → Mode: by Jenkinsfile**, script path defaults to `Jenkinsfile` at repo root.
4. **Scan Multibranch Pipeline Triggers** → enable periodic scan (e.g. every 1 minute) or rely on webhook.
5. **Save** → Jenkins scans the repo and creates one job per branch containing a Jenkinsfile.

**Basic job (Jenkinsfile at repo root):**

```groovy
pipeline {
    agent any
    stages {
        stage('Checkout') {
            steps { checkout scm }
        }
        stage('Build') {
            steps { echo "Building branch: ${env.BRANCH_NAME}" }
        }
        stage('Test') {
            steps { echo 'Running tests...' }
        }
    }
}
```

`env.BRANCH_NAME` lets the same Jenkinsfile behave differently per branch (e.g. only deploy from `main`).

Each branch appears as its own item under the multibranch job in the dashboard, with independent build history.

## 4. Deploy Jenkins on a Server

**Typical production setup (Linux VM):**

1. Install Java (JDK 17):
   ```bash
   sudo apt update && sudo apt install -y fontconfig openjdk-17-jre
   ```
2. Add Jenkins repo & install:
   ```bash
   curl -fsSL https://pkg.jenkins.io/debian-stable/jenkins.io-2023.key | sudo tee /usr/share/keyrings/jenkins-keyring.asc
   echo "deb [signed-by=/usr/share/keyrings/jenkins-keyring.asc] https://pkg.jenkins.io/debian-stable binary/" | sudo tee /etc/apt/sources.list.d/jenkins.list
   sudo apt update
   sudo apt install -y jenkins
   sudo systemctl enable --now jenkins
   ```
3. Jenkins listens on port `8080` by default — open it in the firewall/security group.
4. Retrieve initial password: `sudo cat /var/lib/jenkins/secrets/initialAdminPassword`.

**Docker on a server (simpler, portable):**

```bash
docker run -d --name jenkins --restart unless-stopped \
  -p 8080:8080 -p 50000:50000 \
  -v jenkins_home:/var/jenkins_home \
  jenkins/jenkins:lts
```

**Production considerations:**

- Put **Nginx/Apache reverse proxy** in front with HTTPS (Let's Encrypt).
- Run agents on **separate nodes** (`Manage Jenkins → Nodes → New Node`, connect via SSH or JNLP) so builds don't run on the controller.
- Back up `$JENKINS_HOME` (jobs, credentials, config) regularly.
- Restrict access via **Matrix-based security** or SSO (LDAP/SAML/GitHub OAuth plugin).
- Keep Jenkins + plugins updated (`Manage Jenkins → Plugins → Updates`).

## 5. Jenkinsfile

### 5.1 Connect a git repo to Jenkins

In a Pipeline/Multibranch job config → **Pipeline → Definition: Pipeline script from SCM**:

- SCM: Git
- Repository URL: `https://github.com/org/repo.git` (or SSH URL)
- Credentials: select the stored credential (see section 2)
- Branch: `*/main` (or leave blank for multibranch)
- Script Path: `Jenkinsfile`

Jenkins clones the repo before each build and executes the `Jenkinsfile` found in it — the pipeline logic lives in source control, versioned alongside the code.

### 5.2 Declarative Jenkinsfile

Declarative syntax is structured, opinionated, and easier to read/lint. Skeleton:

```groovy
pipeline {
    agent any

    options {
        timestamps()
        timeout(time: 30, unit: 'MINUTES')
    }

    environment {
        APP_ENV = 'staging'
    }

    stages {
        stage('Checkout') {
            steps { checkout scm }
        }
        stage('Build') {
            steps { sh 'echo Building...' }
        }
        stage('Test') {
            steps { sh 'echo Running tests...' }
        }
        stage('Deploy') {
            when { branch 'main' }
            steps { sh 'echo Deploying to production...' }
        }
    }

    post {
        success { echo 'Pipeline succeeded' }
        failure { echo 'Pipeline failed' }
        always  { echo 'Cleaning up...' }
    }
}
```

Key blocks: `agent` (where it runs), `stages`/`stage` (workflow steps), `when` (conditional stage execution), `post` (actions after build based on result).

### 5.3 Credential fetch using scripted Groovy

Scripted pipelines use raw Groovy with `node`/`stage` blocks — more flexible, useful for complex credential logic. You can even mix a `script {}` block inside a declarative pipeline:

```groovy
node {
    stage('Fetch Credentials') {
        withCredentials([
            usernamePassword(credentialsId: 'db-creds', usernameVariable: 'DB_USER', passwordVariable: 'DB_PASS'),
            string(credentialsId: 'api-token', variable: 'API_TOKEN')
        ]) {
            sh '''
                echo "Connecting as $DB_USER..."
                curl -H "Authorization: Bearer $API_TOKEN" https://api.example.com/health
            '''
        }
    }
}
```

Or fetch programmatically via Groovy's Credentials API (in a scripted block, requires Script Security approval):

```groovy
script {
    def creds = com.cloudbees.plugins.credentials.CredentialsProvider.lookupCredentials(
        com.cloudbees.plugins.credentials.common.StandardUsernamePasswordCredentials.class,
        Jenkins.instance, null, null
    ).find { it.id == 'db-creds' }
    echo "Found credential for user: ${creds.username}"
}
```

Prefer `withCredentials` for normal use — it auto-masks secrets in logs; only reach for the Credentials API for advanced dynamic lookups.

### 5.4 Trigger scripts for deployment to various environments

Combine `when`/`input`/parameters to drive environment-specific deploys from one Jenkinsfile:

```groovy
pipeline {
    agent any
    parameters {
        choice(name: 'ENVIRONMENT', choices: ['dev', 'staging', 'prod'], description: 'Target environment')
    }
    stages {
        stage('Build') {
            steps { sh 'echo Building artifact...' }
        }
        stage('Deploy') {
            steps {
                script {
                    switch (params.ENVIRONMENT) {
                        case 'dev':
                            sh './scripts/deploy.sh dev'
                            break
                        case 'staging':
                            sh './scripts/deploy.sh staging'
                            break
                        case 'prod':
                            input message: 'Approve production deployment?'
                            sh './scripts/deploy.sh prod'
                            break
                    }
                }
            }
        }
    }
}
```

- `parameters`/`choice` lets the user pick an environment at build time.
- `input` pauses the pipeline for manual approval before hitting prod — a common safety gate.
- Each `deploy.sh <env>` script (checked into the repo) encapsulates the actual deployment commands (e.g. `kubectl apply`, `ansible-playbook`, `scp` + `ssh restart service`) parameterized per environment, keeping the Jenkinsfile itself environment-agnostic.

## 6. Real-World Practical Log: Jenkins + React on a RHEL 9 VM

This is a running log of an actual hands-on deployment: Jenkins + a React app, both hosted on a single **RHEL 9** VM, deploying to Bitbucket (org account) instead of GitHub. Kept as a diary of real commands/decisions/gotchas, distinct from the generic notes above.

### 6.1 Environment & Decisions

- **VM OS:** RHEL 9 (`dnf`, `firewalld`, SELinux enforcing by default) — not Ubuntu/CentOS, so some commands differ subtly from generic Linux guides.
- **VM networking:** Private/internal only (hostname like `*.internal-domain`, no public IP) → **Bitbucket webhooks can't reach Jenkins directly**. Chosen trigger: **Poll SCM** (Jenkins periodically checks the repo for new commits, e.g. every 5 min) instead of a push webhook. A tunnel tool (ngrok/smee.io) is noted as an optional future upgrade to get real webhooks.
- **Source control:** Bitbucket repo under an org account (not GitHub) — the app is currently only local, not yet pushed.
- **Serving the React app:** Static build served via **Nginx** (no Node process needed at runtime — Node is only used at _build_ time inside the pipeline).
- **Topology:** Jenkins and Nginx run on the **same VM** — "deploy" is just a local file copy from the Jenkins workspace to the Nginx docroot, not a remote SSH deploy.
- **Credentials handling:** Bitbucket App Password (PAT) will be generated directly in Bitbucket and entered directly into the Jenkins Credentials UI in the browser — never shared in chat/notes.
- **RHEL specifics discovered:** VM uses `dnf` with Red Hat's own repos (`rhel-9-for-x86_64-appstream-rpms`, `baseos-rpms`) plus an org-added `EPEL9` and `custom_rep`. No active Red Hat subscription — installs work fine anyway because packages are being served from these pre-configured repos (not directly from Red Hat's subscription CDN), so subscription status didn't block anything.

### 6.2 Step-by-step commands run

**a) Checked repo availability before installing anything (safe habit on subscription-less/offline systems):**

```bash
dnf repolist
dnf list available git
dnf list available java-17-openjdk
dnf list available nginx
```

Result: all three found in `rhel-9-for-x86_64-appstream-rpms` (git in AppStream/BaseOS, java-17-openjdk in AppStream, nginx in AppStream) — confirmed available before attempting install.

**b) Installed Java 17 (Jenkins requires JDK 11+):**

```bash
sudo dnf install -y java-17-openjdk java-17-openjdk-devel
java -version
```

→ `openjdk version "17.0.20"` confirmed.

**c) Installed Git:**

```bash
sudo dnf install -y git
git --version
```

→ `git version 2.52.0` confirmed.

**d) Installed and started Nginx:**

```bash
sudo dnf install -y nginx
sudo systemctl enable --now nginx
sudo systemctl status nginx
```

→ Active (running), enabled on boot. Confirms Nginx will auto-start after VM reboots.

**e) Installed Node.js via RHEL's module stream system** (RHEL packages Node as a "module" with multiple selectable versions, unlike a single `nodejs` package):

```bash
sudo dnf module list nodejs
```

→ Showed available streams: `18` (default), `20`, `22`, `24`. Chose **stream 22** (Active LTS at time of setup, since 18/20 are older/nearing EOL):

```bash
sudo dnf module enable nodejs:22 -y
sudo dnf install -y nodejs
node -v

```

→ Installed `nodejs 1:22.23.1` (plus `nodejs-libs`, `nodejs-docs`, `nodejs-full-i18n`). **Gotcha:** unlike some distros, `npm` was **not** bundled with the `nodejs` package here — `npm -v` returned "command not found" after installing `nodejs`. Fixed with a separate install:

```bash
sudo dnf install -y npm
```

→ `npm` installed successfully as its own package.

**Base VM prep complete** at this point: Java 17 ✅, Git ✅, Node.js 22 + npm ✅, Nginx (running) ✅.

### 6.3 Key learnings so far

- **What is `dnf`?** It's the package manager for RHEL/CentOS/Fedora (9+/8+) - the tool used to install, update, and remove software (`.rpm` packages) from configured repositories (AppStream, BaseOS, EPEL, custom internal repos, etc.). It's the modern replacement for the older `yum` command (on RHEL 8/9, `yum` is actually just a symlink to `dnf` for backward compatibility). Equivalent tools on other distros: `apt`/`apt-get` (Debian/Ubuntu), `apk` (Alpine), `zypper` (openSUSE). Common usage: `dnf install <pkg>`, `dnf remove <pkg>`, `dnf update`, `dnf list installed`, `dnf repolist` (show configured repos), `dnf module list <pkg>` (show version streams for fast-moving software).
- **`dnf module list <pkg>`** is how RHEL/CentOS 8+ exposes multiple versions of fast-moving software (Node.js, Python, PHP, etc.) instead of just one package version — always check available streams before installing, and explicitly `enable` the desired stream before `dnf install`.
- Running `dnf` commands as a non-root user with `sudo` shows a `"Not root, Subscription Management repositories not updated"` warning — harmless as long as the repos you actually need (AppStream/BaseOS/EPEL/custom) are already configured and enabled; it only means Red Hat's _subscription-specific_ repo refresh was skipped.
- Don't `Ctrl+C` a `dnf` command mid-metadata-download — it just kills the current attempt and you re-run it; no corruption, but wastes time. Let it finish once and results get cached for subsequent commands.
- Nginx's default install already creates and starts a working web server out of the box (`systemctl status nginx` showed "configuration file test is successful" and the default page serving) — no extra setup was needed to get _a_ server running before pointing it at the React build output later.
- _(See Section 6.11 for what `systemctl` is and the full start/stop/status cheat sheet.)_

### 6.5 Jenkins install & the Java-version crash (real troubleshooting story)

**Installed Jenkins from its official repo:**

```bash
sudo wget -O /etc/yum.repos.d/jenkins.repo https://pkg.jenkins.io/redhat-stable/jenkins.repo
sudo rpm --import https://pkg.jenkins.io/redhat-stable/jenkins.io-2023.key
sudo dnf install -y jenkins
sudo systemctl enable --now jenkins
```

→ Installed `jenkins-2.568.2`. Service **failed to start** (`status=1/FAILURE`, restart-looped 5x then gave up: `"Start request repeated too quickly"`).

**Root cause (found via `sudo journalctl -u jenkins --no-pager -n 60`):**

```
Running with Java 17 ..., which is older than the minimum required version (Java 21).
Supported Java versions are: [21, 25]
```

→ This particular Jenkins release (2.568, a recent weekly/LTS build) **requires Java 21+**; Jenkins install guides that say "Java 11/17 is enough" are outdated for current Jenkins versions. Always check `journalctl -u jenkins` first when a Jenkins systemd service fails — the real error is usually right there, not in `/var/log/jenkins/jenkins.log` (that file didn't even exist on this RHEL install; Jenkins on RHEL logs via journald, not a static log file, unless configured otherwise).

**Fix — install Java 21 _alongside_ Java 17, and force Jenkins to use it via a systemd override** (rather than changing the system-wide default `java`, which could affect other tools):

```bash
sudo dnf install -y java-21-openjdk java-21-openjdk-devel
alternatives --list | grep java   # confirmed both 17 and 21 registered

sudo mkdir -p /etc/systemd/system/jenkins.service.d
printf '[Service]\nEnvironment="JENKINS_JAVA_CMD=/usr/lib/jvm/java-21-openjdk/bin/java"\n' | sudo tee /etc/systemd/system/jenkins.service.d/override.conf

sudo systemctl daemon-reload
sudo systemctl reset-failed jenkins
sudo systemctl start jenkins
sudo systemctl status jenkins
```

→ **Success.** `systemctl status jenkins` confirmed `Active: active (running)`, and the `CGroup` line showed the process actually launched via `/usr/lib/jvm/java-21-openjdk/bin/java`, proving the override took effect.

- **Key learnings:**
- `systemd.service.d/override.conf` "drop-in" files are the correct way to customize a packaged systemd service (like overriding the Java binary Jenkins uses) without editing the vendor-provided unit file directly — changes survive package upgrades.
- `journalctl -u <service> --no-pager -n <N>` is the go-to first diagnostic step for _any_ failed systemd service — don't guess, read the log.
- Keep both Java versions installed side by side when a newer app needs a newer JDK but you don't want to risk breaking anything else that might expect the old default.

### 6.6 Working on a shared org VM — safety approach

This VM is **org-owned, shared** infrastructure (not a personal sandbox), so a standing rule was adopted for the rest of this practical: prefer additive/scoped changes over editing shared defaults, never touch host-level security controls (firewalld/SELinux) to "make things easier," verify ports/services are actually free before use, and no destructive commands. Before opening firewall ports, checked what was already running:

```bash
sudo ss -tlnp | grep -E ':80 |:8080 |:8081 '
sudo systemctl list-units --type=service --state=running | grep -iE "nginx|httpd|jenkins|docker"
```

→ Confirmed port 80 was used only by our own freshly-installed Nginx, port 8080 only by our Jenkins, and 8081 was free — nothing pre-existing was at risk. Also discovered `firewalld` isn't even running on this VM (likely managed at the network level by the org instead), so no firewall changes were needed at all.

### 6.9 Webhook vs Poll SCM — internal Bitbucket Server reachability check

The Bitbucket repo lives on an **internal Bitbucket Server/Data Center** instance (`<Your Bitbucket Server URL>`), not public Bitbucket Cloud — meaning webhook traffic stays entirely within the org network, so a real webhook trigger is plausible (unlike with a public-cloud SCM against a private VM).

- Confirmed **outbound** reachability (VM → Bitbucket) first, since Jenkins needs this anyway to clone the repo:

  ```bash
  curl -sk -o /dev/null -w "%{http_code}\n" https://<Your Bitbucket Server URL>/
  ```

  → Returned `302` (redirect to login) — confirms the VM can reach the Bitbucket server.

- **Inbound** reachability (Bitbucket → VM, needed for the webhook itself) can't be tested with a simple curl from one side — the definitive test is Bitbucket Server's own **"Test Connection"** button when adding a webhook, which will be used once the repo + webhook are set up. If that fails (e.g. blocked by network segmentation/VLANs between the Bitbucket server and this VM), fall back to Poll SCM without further network troubleshooting, since requesting firewall changes isn't appropriate for a personal learning exercise on a shared org VM.

### 6.10 "Access from anywhere" - public internet exposure declined

Considered making the deployed React app reachable from the public internet (not just the org network/VPN). Decided against it:

- Publicly exposing an org-owned VM requires firewall/security-group changes at the network perimeter - outside the scope of anything doable from inside the VM, and normally requires explicit IT/Security approval on a corporate machine.
- A publicly reachable internal VM becomes an internet-scannable target, risking the org's network, not just this box.
- Conflicts with the standing safety rule for this exercise (shared VM, don't disrupt/expose anything beyond what's needed for learning).
- Decision: stick to accessing the app via VPN/RDP into the VM, same as Jenkins itself. No tunnel (ngrok/smee.io), no public DNS, no firewall requests. If genuine public hosting is wanted later, the right approach is a separate free-tier service (Vercel/Netlify/personal cloud VM) - not this org VM.

### 6.11 Jenkins service — start / stop / status cheat sheet

**What is `systemctl`?** It's the command-line tool for controlling **systemd**, the init system/service manager used by most modern Linux distros (RHEL, Ubuntu, Fedora, Debian). Systemd is PID 1 - the first process at boot - and manages all background services ("daemons") like Jenkins, Nginx, SSH: starting them in order, restarting them on crash, and tracking their state. `systemctl <verb> <service>` (start/stop/restart/status/enable/disable) is the standard way to control any service on these systems - it replaced older init.d/`service` tooling from older distros.

Jenkins is installed as a native systemd service on this RHEL VM, so it's managed with `systemctl` like any other service:

```bash
# Start Jenkins
sudo systemctl start jenkins

# Stop Jenkins
sudo systemctl stop jenkins

# Check if it's running (full status, recent logs, PID, memory)
sudo systemctl status jenkins

# Quick yes/no check only
sudo systemctl is-active jenkins

# Restart (stop + start in one go) - useful after config/override changes
sudo systemctl restart jenkins

# Confirm it will auto-start on VM reboot
sudo systemctl is-enabled jenkins

# Tail recent logs if something looks wrong
journalctl -u jenkins --no-pager -n 50
```

Note: since our systemd drop-in override (`/etc/systemd/system/jenkins.service.d/override.conf`) forces Jenkins onto Java 21, any edit to that override file requires `sudo systemctl daemon-reload` before the next `restart` for the change to take effect.

### 6.12 Login lockout — turned out to be wrong username, not a reset

Hit `loginError` at `http://<Your VM IP>:8080/loginError` using previously-noted credentials. Before touching any Jenkins config, diagnosed non-destructively:

```bash
sudo ls -la /var/lib/jenkins/users/                                   # confirms the user folder exists
sudo cat /var/lib/jenkins/users/*/config.xml | grep -i "<id>\|<fullName>"  # shows the *actual* stored username
```

**Root cause:** simply using the wrong username (not a lost/reset account, not a Jenkins bug). The `<id>` field in the user's `config.xml` is the definitive source of truth for the exact login username Jenkins has on record — safer to check this than rely on memory.
**Key learning:** always verify the exact username straight from `/var/lib/jenkins/users/*/config.xml` before assuming account/security state is broken — avoids an unnecessary security reset on a shared VM.

### 6.13 Local machine Node.js setup - nvm-windows symlink issue (no admin rights)

Local Windows machine had **nvm-windows** managing 3 Node versions (18.20.2 / 22.23.1 / 24.18.0), but `nvm use 22.23.1` appeared to succeed while `node`/`npm` still resolved to the old broken/missing state - because nvm-windows updates a symlink at `C:\nvm4w\nodejs` pointing at the active version, and creating/updating that symlink needs elevated (admin) permissions, which weren't available.

- **Root cause of the original error** (`npm create vite` failing with `SyntaxError: ... does not provide an export named 'styleText'`): local Node was v18.20.2, but the current `create-vite` package requires Node 20+ (uses a `node:util` API added later). Not a mistake in the command - just an outdated Node version.
- **Workaround without admin rights:** bypass the nvm symlink entirely and call the specific version's `node.exe` directly from nvm's version folder:
  ```powershell
  nvm root                     # shows nvm's base storage folder, e.g. C:\Users\<user>\AppData\Roaming\nvm
  Get-ChildItem "<nvm root>" -Name   # lists installed version folders, e.g. v22.23.1
  ```

### 6.16 What is Nginx, and why do we need it?

**What it is:** Nginx is a **web server** - a program that listens on a network port (e.g. 80, 8081) and responds to HTTP requests by serving files or forwarding ("proxying") requests to another backend service. It's especially good at serving **static files** (HTML/CSS/JS/images) efficiently and acting as a **reverse proxy** in front of application servers.

**Is it strictly required?** No - alternatives exist for serving a React build:

- A tiny Node process (`npx serve dist`) could serve the same static files.
- Apache, Caddy, or even Python's `http.server` could do the same job.

**What happens without it (in our case)?** A React build (`npm run build`) produces static files (`dist/index.html`, `.js`, `.css`) - nothing runs them automatically; _something_ must serve those files over HTTP so a browser can fetch them. Without Nginx we'd need to keep a small Node process running permanently just to serve files - possible, but less efficient and less standard than a dedicated web server.

**Why Nginx specifically:** it's fast, lightweight, battle-tested for static content, doesn't need a Node/runtime process just to serve files, and is the most common production choice for this exact job (serving a built SPA).

**How it's configured (at a basic level):** Nginx reads `.conf` files describing **server blocks** - each one says "listen on port X, serve files from folder Y (docroot)". Multiple server blocks can coexist (different ports/domains) without interfering with each other, e.g.:

```nginx
server {
    listen 8081;               # port to listen on
    server_name _;              # matches any hostname
    root /usr/share/nginx/react-app;   # docroot - where the static files live
    index index.html;           # default file to serve
    location / {
        try_files $uri $uri/ /index.html;  # needed for SPA client-side routing
    }
}
```

Nginx can do much more (SSL termination, load balancing, reverse-proxying to APIs) - but for this project it's only doing one job: serving the React app's static build output on a dedicated port.

**Important distinction: Nginx is NOT a "Node/backend" server.** It's easy to assume "the files come from a server, so that server must be running Node" - that's not right:

- A **backend (app-logic) server** = a program that executes code per request, has APIs, talks to a database (e.g. Node/Express, Python/Django). Dynamic - runs logic every time.
- **Nginx here** = purely a file server. It hands out the exact static bytes of `dist/index.html`, `.js`, `.css` from disk, unchanged, with zero code execution or logic - the same job a USB drive would do if it could serve HTTP. It doesn't know or care that React was involved in producing those files.
- **The React code itself is 100% frontend** - it only actually _runs_ once it reaches the user's browser (that's the definition of a client-side framework). Nginx is just the delivery mechanism, like a librarian handing over a book; the "reading" (execution) happens in the browser, not on the server.
- If this app later needed to call APIs (fetch/save data), _that_ would require a real backend app server running separately (Node/Express, etc.) - Nginx could even reverse-proxy in front of it - but our current demo app is purely static with no backend API, so Nginx alone is sufficient.

### 6.18 Jenkinsfile — declarative, styled after a real-world multi-env template

Wanted the Jenkinsfile to mimic a fuller real-world shape (Checkout → Install → Lint → Build → per-environment Deploy stages) rather than a bare-minimum version — ties directly into practical items 3 (Multibranch Pipeline) and 5 (deploy scripts per environment) from the original curriculum.

```groovy
pipeline {
    agent any

    tools {
        nodejs 'Node22'
    }

    environment {
        DEPLOY_DIR = '/usr/share/nginx/react-app'
        BRANCH_NAME = 'main'   // manual override: see caveat below
    }

    stages {
        stage('Checkout') {
            steps {
                checkout scm
            }
        }

        stage('Install Dependencies') {
            steps {
                sh 'npm install'
            }
        }

        stage('Lint') {
            steps {
                sh 'npm run lint'
            }
        }

        stage('Build App') {
            steps {
                sh 'npm run build'
            }
        }

        stage('Deploy to DEV') {
            when { branch 'dev' }
            steps {
                echo 'Deploying to DEV... (placeholder - activate with Multibranch Pipeline + dev branch)'
            }
        }

        stage('Deploy to UAT') {
            when { branch 'uat' }
            steps {
                echo 'Deploying to UAT... (placeholder - activate with Multibranch Pipeline + uat branch)'
            }
        }

        stage('Deploy to PROD') {
            when { branch 'main' }
            steps {
                sh '''
                    rm -rf ${DEPLOY_DIR}/*
                    cp -r dist/* ${DEPLOY_DIR}/
                '''
            }
        }
    }

    post {
        success {
            echo 'Build succeeded!'
        }
        failure {
            echo 'Build failed!'
        }
    }
}
```

**Confirmed `package.json` scripts** (fresh Vite React scaffold): `dev`, `build`, `lint` (`eslint .`), `preview` — **no `test` script**, so a "Run Tests" stage was intentionally omitted (trivial to add later once a test framework + `"test"` script exist).

**Key caveats/learnings:**

- **`when { branch '<name>' }` only auto-works with a Multibranch Pipeline job** — that job type sets the `BRANCH_NAME` environment variable per-branch automatically. A plain single Pipeline job (what we're creating now, pointed only at `main`) does _not_ set `BRANCH_NAME` on its own — the `when` condition would silently evaluate false and skip the deploy stage entirely. **Workaround used:** manually set `BRANCH_NAME = 'main'` in the `environment {}` block so `when { branch 'main' }` evaluates true today. Once a real Multibranch Pipeline with `dev`/`uat`/`main` branches is built later (practical item 3), this manual override should be removed — Jenkins will populate `BRANCH_NAME` correctly on its own per branch.
- The `dev`/`uat` deploy stages are intentionally **placeholders** (`echo` only) since those branches don't exist yet in this repo — they'll become real once the Multibranch Pipeline practical is done.
- Deploy step is a **local file copy** (`cp -r dist/* $DEPLOY_DIR/`), not a remote SSH deploy, since Jenkins and Nginx share this VM.

### 6.20 🚨 GOTCHA: Bitbucket PAT containing a `/` character breaks git HTTP auth (even though the token is 100% valid)

Jenkins' "Failed to connect to repository" error (`Authentication failed`) turned out to be one of the trickiest bugs so far — the token and username were completely correct the whole time, but git's own HTTP auth handling silently failed because of one specific character in the token.

**Diagnostic trail (in order, with exact commands used):**

1. `git ls-remote` interactively (typing/pasting the token at the password prompt) → `fatal: Authentication failed`. Assumed token or username was wrong.
   ```bash
   git ls-remote -h https://<Your Username>@<Your Bitbucket Server URL>/scm/~<Your Username>/jenkins-react.git HEAD
   # prompted: Password for 'https://<Your Username>@<Your Bitbucket Server URL>':  <- pasted the token here
   # fatal: Authentication failed for '.../jenkins-react.git/'
   ```
2. Tested the _same_ token via `curl` against a generic info endpoint → returned valid JSON. **Misleading false-positive** — this specific endpoint is public/unauthenticated in Bitbucket Server, so it doesn't actually validate credentials at all!
   ```bash
   curl -sk -u "<Your Username>:TOKEN" https://<Your Bitbucket Server URL>/rest/api/1.0/application-properties
   # {"version":"7.21.5", ...}  <- looked like success, but this endpoint doesn't require valid auth
   ```
3. Tested against a real authenticated, resource-specific endpoint instead → returned full repo metadata successfully. This proved the token + username + permissions were **genuinely valid**.
   ```bash
   curl -sk -u "<Your Username>:TOKEN" https://<Your Bitbucket Server URL>/rest/api/1.0/projects/~<Your Username>/repos/jenkins-react
   # {"slug":"jenkins-react", ..., "project":{"key":"~<Your Username>", ...}}  <- genuine proof of valid auth
   ```
4. So the problem was isolated to git's HTTP auth path specifically, not the token/permissions. Tried embedding the token directly in the clone URL to bypass the interactive prompt:

   ```bash
   git ls-remote -h "https://<Your Username>:TOKEN@<Your Bitbucket Server URL>/scm/~<Your Username>/jenkins-react.git" HEAD
   # fatal: unable to access '...': URL using bad/illegal format or missing URL
   ```

   → because the token contained a literal **`/`** character, which broke URL parsing (a `/` in the password segment of a URL is ambiguous with a path separator).

5. Retried the same URL-embed test but with the `/` percent-encoded as `%2F`:
   ```bash
   git ls-remote -h "https://<Your Username>:TOKEN_WITH_SLASH_AS_%2F@<Your Bitbucket Server URL>/scm/~<Your Username>/jenkins-react.git" HEAD
   echo "Exit code: $?"
   # Exit code: 0   <- success!
   ```

**Root cause:** the PAT happened to contain a `/` character. Bitbucket/git's credential handling for HTTP(S) git operations doesn't cleanly support a raw, un-encoded `/` inside a password/token in certain input paths (interactive prompt, credential helpers) — even though the exact same token works perfectly fine via `curl -u` (which handles Basic Auth encoding differently/correctly regardless of special characters).

**Fix:** simply regenerate the PAT until you get one without a `/` in it (tokens are random strings — usually only takes a retry or two). Update the credential (Jenkins' stored credential and/or local git credential) with the clean token.

**Key learnings:**

- **A curl/REST "success" doesn't always prove a token is valid** — some endpoints (like `application-properties`) are public and return data regardless of auth. Always test against a real authenticated, resource-specific endpoint (e.g. a specific repo/project API) to truly validate credentials.
- **Special characters in tokens/passwords (especially `/`, `@`, `:`) can break naive URL-embedding or certain credential-handling code paths**, even when the exact same secret works fine through other auth mechanisms (like curl's `-u` flag, which handles Basic-Auth encoding internally). If auth mysteriously fails despite a confirmed-valid token, suspect special characters next.
- **Isolate variables one at a time**: test the token outside git (curl), test the URL format separately (embed directly, percent-encode), before assuming the credential itself is broken. This systematic narrowing is what found the real cause instead of endlessly regenerating tokens blindly.

### 6.23 Webhook attempt — deep-dive into a real CSRF/plugin-compatibility issue, then a safety-conscious fallback to Poll SCM

Tried hard to get a real webhook working (since internal Bitbucket Server + Jenkins staying within the org network made it plausible), and hit a genuinely tricky, multi-layered issue:

1. **First attempt** — Bitbucket's built-in `/bitbucket-hook/` endpoint (before the dedicated plugin was installed) → `403 No valid crumb was included in the request`. Looked like a CSRF/crumb issue.
2. **Tried Jenkins' generic "Trigger builds remotely" token URL** (`/job/<name>/build?token=...`) instead → first got `403 ... Permission you need to have (but didn't): hudson.model.Hudson.Read` — this was actually a _different_, clearer problem: **anonymous users have zero read/build permission** on this Jenkins instance (standard, sensible default security posture — not something to weaken just for convenience).
3. **Embedded a real Jenkins user + API token via Basic Auth in the URL** (`http://user:apitoken@host:8080/job/.../build?token=...`) → authentication succeeded (confirmed via a direct `curl -I` test returning `201 Created`), but Bitbucket's own webhook call to the _same_ URL still hit the **crumb 403 again** — meaning authentication worked, but CSRF crumb enforcement still applied to this generic endpoint (unlike the common assumption that API-token/Basic-Auth requests are automatically crumb-exempt in Jenkins — they are **not**, by default).
4. **Installed the proper "Bitbucket Server Integration" plugin** (previously missing entirely — confirmed via Manage Jenkins → Plugins → Installed) to get a purpose-built, supposedly crumb-exempt `/bitbucket-hook/` endpoint with a native "Bitbucket webhook trigger" job option. Configured it correctly (Push event, proper URL) — **still hit the exact same crumb 403.** This points to a genuine **plugin/Jenkins-core version incompatibility** — the plugin's `CrumbExclusion` registration likely hasn't kept pace with Jenkins 2.568.2's core CSRF hardening changes. A known class of problem with more niche/less-frequently-updated plugins (vs. e.g. the far more actively maintained GitHub plugin, which is less likely to hit this specific issue).
5. **Considered the last remaining lever:** globally disabling "Prevent Cross Site Request Forgery exploits" in Jenkins security settings. Explicitly discussed the blast radius (instance-wide CSRF protection loss; on a shared VM, this widens risk since Jenkins pipelines already run shell commands as the `jenkins` system user — a successful CSRF exploit could pivot beyond just this one job). **Decision: not worth it** — this crosses from "scoped, reversible learning tweak" into "meaningfully weakens security for a shared system," which conflicts with the standing safety rule for this VM.

**Final decision: use Poll SCM instead.**

```
Build Triggers → uncheck "Bitbucket webhook trigger" and "Trigger builds remotely"
Build Triggers → check "Poll SCM"
Schedule: H/5 * * * *
```

This still gives fully automatic builds on every push (checked every ~5 minutes instead of instantly) with zero security tradeoffs and no plugin-compatibility fighting.

**Key learnings:**

- **A `403 crumb` error and a `403 permission denied` error look similar but mean very different things** — always read the exact message body (crumb vs. explicit "Permission you need to have...") to know which layer is actually failing.
- **API-token/Basic-Auth requests are NOT automatically exempt from Jenkins' CSRF crumb check** — that's a common misconception; the _actual_ exemption mechanism is a plugin explicitly registering a `CrumbExclusion` for its own dedicated webhook endpoint, not a blanket auth-based bypass.
- **Plugin-provided crumb exemptions can break silently when Jenkins core changes CSRF internals faster than a less-popular plugin is updated** — this is more likely with smaller/niche plugins (Bitbucket Server Integration) than heavily-used ones (GitHub plugin).
- **Poll SCM is a completely legitimate, production-grade fallback** — many real enterprises with strict internal networks/security policies (exactly this scenario) use it deliberately, not just as a "beginner" option.
- **Knowing when to stop pushing on a fix is itself a valuable skill** — recognized that the next available fix (disabling CSRF instance-wide) had a real, disproportionate security cost relative to the benefit (instant vs. 5-minutes-delayed build triggering), and made the safer call.

### 6.25 Poll SCM confirmed working — clarifying "only 1 build in an hour" (expected, not a bug)

- Full poll history (including "no changes found" checks) is viewable at `http://<Your VM IP>:8080/job/<job-name>/pollLog/`.
