# Plan: Multibranch Pipeline — Multi-Environment Simulation

**Builds on:** the completed Jenkins + React single-branch practical (see `plan.md`, `3. Jenkins.md`, `Notes.md`). This is a separate, standalone plan for the next phase — kept in its own file so the original practical's plan stays untouched as historical record.

## ⚠️ Standing Safety Constraint (same as before — still a shared org VM)

- **Never** modify system-wide defaults if a scoped/local alternative exists.
- **Never** enable/disable/reconfigure host-level security controls (firewalld, SELinux mode, etc.).
- **Check before assuming a resource (port, path, service) is free** — verify nothing else is using it before claiming it.
- **Prefer additive changes** (new files, new server blocks, new directories) over editing/overwriting anything pre-existing.
- **No destructive commands** (no `rm -rf` outside our own dedicated docroots, no truncating/overwriting shared configs, no killing unrelated processes).
- If ever unsure whether a step could affect shared/other infrastructure on this VM, pause and ask the user before proceeding.

## Problem / Goal

Practice a **realistic multi-environment enterprise pipeline pattern** — 3 branches (`main`/`uat`/`production`) each auto-deploying to their own "environment" — without needing 3 separate VMs. Since only one shared VM is available, **simulate 3 environments using 3 different ports** on the same VM, each with its own isolated Nginx site/docroot. This lets us practice the real mechanics (Multibranch Pipeline job type, native `BRANCH_NAME`, per-branch `when` conditions, and an approval gate before prod) that a true multi-VM setup would use, just with `localhost:<port>` standing in for `dev-vm`/`uat-vm`/`prod-vm`.

**Dropped from consideration:** a separate Windows/WSL2 environment for this phase — staying on the existing RHEL VM.

**Honest framing (discussed with user):** in real production, separate VMs/servers per environment are the dominant pattern for anything customer-facing — full isolation, independent scaling, different security postures. Same-VM-different-ports is a real but narrower pattern (lightweight internal tools, cost-constrained setups, temporary staging before a service "graduates" to its own infra) — not how most genuine prod environments are run, precisely because a shared VM means shared blast radius. This phase is explicitly a **learning simulation** of the pipeline _logic_, not a claim that this is how real prod infra should look.

## Confirmed decisions

- **Same VM, same Jenkins instance** — no new infrastructure.
- **3 "environments" simulated via 3 ports:**
  | Branch | Simulated environment | Port | Docroot |
  | -------------- | --------------------- | ------------------------------------------------ | ----------------------------------- |
  | `main` | Dev | 8081 (already exists from the earlier practical) | `/usr/share/nginx/react-app` |
  | `uat` | UAT | 8082 (new) | `/usr/share/nginx/react-app-uat` |
  | `production` | Prod | 8083 (new) | `/usr/share/nginx/react-app-prod` |
- **Job type:** switch from single Pipeline to a **Multibranch Pipeline** job, so `BRANCH_NAME` is set natively per branch (no manual override needed, unlike the earlier Jenkinsfile).
- **Trigger:** keep **Poll SCM** (same reasoning as before — no public network reachability for a webhook).
- **Safety gate:** add a manual **approval step** (`input`) before the "production" deploy stage, matching real-world practice.

## Approach / Todos

1. **Create `uat` and `production` branches** in the Bitbucket repo (from `main`).
2. **Prepare Nginx for UAT and Prod ports** — new isolated server blocks (8082, 8083) and docroots, following the same additive pattern as the existing 8081 site; verify ports are free first.
3. **Update the Jenkinsfile** — branch-aware deploy stages (`when { branch 'main' }` / `'uat'` / `'production'`), each copying `dist/*` to its own docroot; add an `input` approval gate before the production deploy stage.
4. **Convert the Jenkins job to a Multibranch Pipeline** — point it at the same Bitbucket repo; Jenkins auto-discovers `main`/`uat`/`production` and creates a sub-job per branch.
5. **Configure Poll SCM** on the Multibranch Pipeline.
6. **Test each branch independently** — push to `main`, confirm deploy to 8081; push to `uat`, confirm deploy to 8082; push to `production`, confirm the pipeline pauses for approval, then deploys to 8083 after clicking "Deploy".
7. **Verify all three apps are simultaneously live** — `http://<Your VM IP>:8081`, `:8082`, `:8083` all serving independently.

## Notes / Considerations

- This is a **simulation** of multi-VM deployment, not a literal one — the Jenkinsfile logic (branch detection, per-environment targets, approval gates) is identical to what a real multi-VM setup would use; only the deploy _destination_ differs (local port vs. remote SSH host). This still gives full hands-on practice with the actual pipeline mechanics.
- Real multi-VM deploys would use `scp`/`ssh` with per-environment credentials (see the "Advanced Reference" section in `Notes.md` for that design) — optionally, a **local SSH loopback** (SSH to `localhost` with a dedicated deploy user) could be layered in later to practice the SSH-credential mechanics too, without needing real separate VMs. Not required for this phase's core goal.
