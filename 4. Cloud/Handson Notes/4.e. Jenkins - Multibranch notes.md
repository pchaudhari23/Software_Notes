# Multibranch Pipeline — Multi-Environment Simulation

A hands-on practical building on the completed single-branch Jenkins + React project (see `3. Jenkins.md` and `Notes.md`). This document tracks the **realistic multi-environment enterprise pipeline pattern** — 3 branches, each deploying to its own "environment" — simulated on a single shared VM using different ports instead of separate VMs.

For full background/setup (VM, Jenkins install, base Nginx config, credentials, etc.), see the earlier artifacts — this file covers only what's new for this phase.

## Sidenote: What is a CI/CD pipeline?

**CI/CD** stands for **Continuous Integration / Continuous Delivery (or Deployment)** — a practice of automating the steps between "developer pushes code" and "code is running/available," so this happens consistently and without manual intervention every time.

- **CI (Continuous Integration):** every time code is pushed, it's automatically **built and tested** (e.g. `npm install`, `npm run lint`, `npm run build`). This catches breakages early — the moment they're introduced, not days later.
- **CD (Continuous Delivery/Deployment):** once the build passes, the result is automatically **deployed** somewhere — a server, a hosting platform, etc. "Delivery" often implies a manual approval step before production; "Deployment" implies it goes out fully automatically, even to production.

A **pipeline** is the defined sequence of these automated steps (checkout → install → lint → build → deploy), typically described as code (a `Jenkinsfile`, in our case) so the process is version-controlled, repeatable, and reviewable like any other code change.

**What we already built (earlier in this session) is a genuine, working CI/CD pipeline:**

```
Bitbucket (push) → Jenkins (Poll SCM detects it) → checkout → npm install → lint → build → deploy → Nginx serves the app
```

This phase (Multibranch Pipeline + multi-environment simulation) is an **enhancement** to that same pipeline — adding multiple branches, each mapped to its own "environment," plus a manual approval gate before the simulated "production" deploy. This is exactly the kind of CI/CD maturity step real teams take: starting with one branch/one environment, then expanding into a full dev → UAT → prod promotion flow as needs grow.

## Goal

Practice the real mechanics of an enterprise multi-environment pipeline:

- **Multibranch Pipeline** job type (Jenkins auto-discovers branches, sets `BRANCH_NAME` natively)
- **Per-branch deploy stages** (`when { branch '...' }`)
- **A manual approval gate** before production deploys

...without needing 3 separate VMs — this VM plays the role of "dev VM", "UAT VM", and "prod VM" simultaneously, distinguished only by port number.

## Step 3: Updated Jenkinsfile — branch-aware deploy stages + approval gate ✅

Replaced the Phase 1 Jenkinsfile (which had a manual `BRANCH_NAME = 'main'` override) with a branch-aware version:

```groovy
pipeline {
    agent any
    tools { nodejs 'Node22' }

    stages {
        stage('Checkout')           { steps { checkout scm } }
        stage('Install Dependencies') { steps { sh 'npm install' } }
        stage('Lint')                { steps { sh 'npm run lint' } }
        stage('Build App')           { steps { sh 'npm run build' } }

        stage('Deploy to DEV') {
            when { branch 'main' }
            environment { DEPLOY_DIR = '/usr/share/nginx/react-app' }
            steps { sh 'rm -rf ${DEPLOY_DIR}/* && cp -r dist/* ${DEPLOY_DIR}/' }
        }

        stage('Deploy to UAT') {
            when { branch 'uat' }
            environment { DEPLOY_DIR = '/usr/share/nginx/react-app-uat' }
            steps { sh 'rm -rf ${DEPLOY_DIR}/* && cp -r dist/* ${DEPLOY_DIR}/' }
        }

        stage('Approval for PROD') {
            when { branch 'production' }
            steps { input message: 'Deploy to PRODUCTION (port 8083)?', ok: 'Deploy' }
        }

        stage('Deploy to PROD') {
            when { branch 'production' }
            environment { DEPLOY_DIR = '/usr/share/nginx/react-app-prod' }
            steps { sh 'rm -rf ${DEPLOY_DIR}/* && cp -r dist/* ${DEPLOY_DIR}/' }
        }
    }

    post {
        success { echo 'Pipeline succeeded!' }
        failure { echo 'Pipeline failed — check console output.' }
    }
}
```

Key changes from Phase 1: removed the manual `BRANCH_NAME` override (Multibranch job type will set it natively per branch), added real `cp -r` deploy stages for DEV/UAT/PROD each targeting its own docroot/port, and added an `input` approval gate before the PROD deploy. Full reasoning + steps documented in `Jenkinsfile-multibranch-reference.md`.

Pushed to all three branches (`main`, `uat`, `production`) — content is identical across branches; only the `when { branch '...' }` condition determines which stage actually runs at execution time.

## Step 4: Converting to a Multibranch Pipeline job ✅

Created a new job **`jenkins-react-multibranch`** (New Item → Multibranch Pipeline). Under Branch Sources, used a plain **Git** source (not "Bitbucket Server" — that option requires registering a separate Bitbucket Server instance under Manage Jenkins, extra complexity we didn't need since the original job already worked fine with plain Git + credentials).

**Gotcha hit:** first attempt entered the _browser_ repo URL (`.../users/<user>/repos/jenkins-react/browse`) instead of the actual git clone URL — this caused a SAML SSO redirect and a `FATAL: Failed to recompute children` error (`fatal: unable to update url base from redirection`) in the Scan Repository Log. Fixed by using the real clone URL in `/scm/~<username>/<repo>.git` format (confirmed via `git remote -v` on the VM), same as the original Phase 1 job used.

After the fix, **Scan Repository Log showed success**:

```
Checking branches...
  Checking branch production → 'Jenkinsfile' found → Met criteria → Scheduled build
  Checking branch main       → 'Jenkinsfile' found → Met criteria → Scheduled build
  Checking branch uat        → 'Jenkinsfile' found → Met criteria → Scheduled build
Processed 3 branches
Finished: SUCCESS
```

All three branches auto-discovered as sub-jobs, each triggering an initial build automatically — confirming `BRANCH_NAME` is now set natively per branch (no manual override needed, unlike Phase 1).

**Also stopped Poll SCM on the old `jenkins-react-demo` single-Pipeline job** (Configure → Build Triggers → unchecked Poll SCM → Save) before creating the new job, since it's being superseded and there was no reason to keep two jobs polling the same repo.

## Step 5: Poll SCM on the Multibranch job ✅

Configured at the top-level `jenkins-react-multibranch` job (not per-branch): **Configure → Scan Multibranch Pipeline Triggers → checked "Periodically if not otherwise run" → Interval: 2 minutes** (shortened from the realistic 5 min just for faster testing during this practical — easy to bump back up later).

This single setting both re-scans for new/removed branches **and** triggers a build on any branch with new commits — the multibranch equivalent of the single-job "Poll SCM" checkbox, but repo-wide across all branches at once.

## Sidenote: Poll SCM load — the original single-Pipeline job

Worth recording for realism/awareness: after configuring **Poll SCM** (`H/5 * * * *`) on the original `jenkins-react-demo` job (single Pipeline, Phase 1), it polled the repo roughly **every 5 minutes, continuously, for several days** — completely independent of whether anyone was actively working in a session or not. This is because Poll SCM is a server-side cron-like schedule tied to the Jenkins service being up, not to any user's activity.

Each poll is lightweight (an SCM changelog check, not a full build) so it isn't "wasted" in a heavy sense, but it is genuinely continuous background load for as long as the trigger stays configured. The full history of every poll attempt (not just ones that triggered a build) is viewable per-job at `http://<Your VM IP>:8080/job/<job-name>/pollLog/`. This was the direct motivation for **unchecking Poll SCM** on that old job once it was superseded by the new Multibranch Pipeline (see Step 4) — no reason to keep two jobs continuously polling the same repository.

## Concepts specific to this phase

### Multibranch Pipeline vs. single Pipeline

A **single Pipeline job** (used in the earlier practical) tracks exactly one branch — `BRANCH_NAME` isn't set automatically, which is why the earlier Jenkinsfile needed a manual `environment { BRANCH_NAME = 'main' }` override for its `when` conditions to work.

A **Multibranch Pipeline job** scans the entire repository, automatically creates a sub-job for every branch it finds (that contains a Jenkinsfile), and sets `BRANCH_NAME` correctly and natively for each one — no manual override needed. This is the correct job type whenever a Jenkinsfile needs to behave differently per branch, which is exactly this scenario.

### The `input` step (manual approval gate)

```groovy
stage('Approval for PROD') {
    when { branch 'production' }
    steps {
        input message: 'Deploy to PRODUCTION?', ok: 'Deploy'
    }
}
```

This pauses pipeline execution and waits for a human to click a button in the Jenkins UI before continuing — the standard real-world safety gate between automated lower environments (dev/UAT) and production. If nobody approves, the pipeline stays paused indefinitely (or times out, if configured).

### Simulating multi-VM with ports (and the honest limitation)

Using different ports on one VM is a legitimate way to practice pipeline _logic_ (branching, conditionals, environment-specific values) cheaply. The one thing it does **not** teach: real remote-deploy mechanics (SSH credentials, host key verification, network reachability between Jenkins and a separate target machine) — since everything here stays on `localhost`. That gap is optionally addressed later via a **local SSH loopback** (SSH to `localhost` using a dedicated deploy user) if we want that specific practice without provisioning real additional VMs.
