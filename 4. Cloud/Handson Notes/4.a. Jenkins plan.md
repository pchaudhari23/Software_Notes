# Plan: Deploy Jenkins + React App on a CentOS/RHEL VM

⚠️ Standing Safety Constraint (applies to ALL steps below)

This VM is an **org-owned shared machine**, not personal — used for a personal learning exercise, but NOT dedicated to it. Other people/processes/teams may depend on this machine. For every step from here on:

- **Never** modify system-wide defaults if a scoped/local alternative exists (e.g., install new Java versions alongside existing ones rather than replacing; use systemd drop-in overrides scoped to one service rather than editing shared configs).
- **Never** enable/disable/reconfigure host-level security controls (firewalld, SELinux mode, etc.) that could affect other users' setups — treat their current state as intentional and work around it, don't "fix" it.
- **Check before assuming a resource (port, path, service) is free** — verify nothing else is using it before claiming it.
- **Prefer additive changes** (new files, new server blocks, new directories) over editing/overwriting anything pre-existing (e.g., don't overwrite Nginx's default docroot/config — add a separate site/port for the React app instead).
- **No destructive commands** (no `rm -rf`, no truncating/overwriting shared configs, no killing unrelated processes).
- If ever unsure whether a step could affect shared/other infrastructure on this VM, pause and ask the user before proceeding.

## Problem / Goal

Set up a single CentOS/RHEL VM that hosts both Jenkins (CI/CD server) and a React app, so pushing code to Bitbucket eventually results in the built React app being served by Nginx on that VM. This is a hands-on practical to reinforce the Jenkins notes (install, credentials, Jenkinsfile, deployment stages).

## Confirmed decisions

- **OS:** CentOS/RHEL (uses `yum`/`dnf`, `firewalld`, `SELinux` — different from Debian/Ubuntu steps in the notes).
- **Source control:** React app will be pushed to a **new Bitbucket repo** (org account, not currently in git).
- **Serving:** Build the React app (`npm run build`) and serve the static output with **Nginx** (no Node process at runtime).
- **Topology:** Single VM running both Jenkins and Nginx — the "deploy" step is a local file copy on the same machine, not a remote SSH deploy.
- **Trigger:** VM is **privately networked** (no public IP), so a Bitbucket webhook cannot reach Jenkins directly. Default to **Poll SCM** (Jenkins periodically checks Bitbucket for new commits, e.g. every 5 min). Optional stretch goal noted below: use ngrok/smee.io to tunnel a real webhook for extra practice.

## Approach / Todos

1. **Push React app to Bitbucket** — init git repo locally, create a new Bitbucket repo (org account), push `main` branch.
2. **Prepare the VM** — install Java (JDK 17), git, Node.js + npm, Nginx via `dnf`/`yum`; enable/start `nginx`.
3. **Install Jenkins on the VM** — add Jenkins yum repo, `dnf install jenkins`, enable as systemd service, open port 8080, unlock via initial admin password, install suggested + Git/Pipeline/NodeJS plugins.
4. **Configure Jenkins basics** — create admin user; add **NodeJS** tool under Global Tool Configuration (so pipeline can use `npm`).
5. **Add Bitbucket credentials** — store a Bitbucket App Password (or SSH key) in Jenkins Credentials so it can pull the repo.
6. **Prepare Nginx docroot + permissions** — create a docroot (e.g. `/usr/share/nginx/html/react-app`), and handle CentOS-specific gotchas: SELinux context (`restorecon`/`chcon`) and giving the `jenkins` user rights to write there (e.g. group ownership + passwordless `sudo cp`/`rsync` scoped to that path via `visudo`), plus `firewall-cmd` to open port 80 (and 8080 for Jenkins UI).
7. **Write the Jenkinsfile** (declarative) in the repo: stages for Checkout → Install deps (`npm ci`) → Build (`npm run build`) → Deploy (copy `build/` to the Nginx docroot, restart/reload Nginx if needed) → post block for success/failure notification.
8. **Create the Jenkins Pipeline job** — "Pipeline script from SCM" pointing at the Bitbucket repo/Jenkinsfile; set **Poll SCM** trigger schedule (e.g. `H/5 * * * *`).
9. **Run and verify** — trigger a build, confirm console output succeeds, browse to `http://<vm-ip>` and confirm the React app loads; make a small code change, push, and confirm Poll SCM picks it up and redeploys.
10. _(Optional / stretch)_ Document how to swap Poll SCM for a real Bitbucket webhook using ngrok or smee.io, for future reference.

## Decision log

- **Repo location — personal Bitbucket namespace only.** User explicitly does not want the React app repo inside any shared org project. Using Bitbucket Server's built-in personal project (`~username`), private by default, created via the UI (Create → Repository, personal project). No MCP repo-creation used — user creates it themselves.
- **Public internet access — declined.** User asked about accessing the deployed app "from anywhere" (public internet). Flagged that this requires network-perimeter firewall changes and IT/Security approval on an org-owned VM, and conflicts with the standing safety constraint. User chose to **stick with VPN/RDP-only access** for this learning exercise — no public exposure will be attempted.

## Notes / Considerations

- CentOS/RHEL specifics that differ from the earlier (Debian-based) notes: package manager (`dnf`/`yum` vs `apt`), `firewalld` instead of `ufw`, and **SELinux** enforcing mode can silently block Nginx from serving files or Jenkins from writing to them — plan explicitly accounts for this.
- Because Jenkins and the deploy target are the same VM, no SSH-based remote deploy or extra deploy credentials are needed for this iteration — keeps the first working pipeline simple. Multi-environment (dev/staging/prod) deploy scripts from the earlier notes can be layered on later once this single-VM flow works.
- Poll SCM was chosen over webhook due to the VM's private networking; this does mean up to a few minutes of delay between a push and a build starting, which is acceptable for learning purposes.
